# 코쓱톤 아이디어 총정리 v2 (2026-09-19)

> 변경 이력: v1은 "연락 전 가능 여부 확인(노크)"이었으나 **주제 '교류'에 비해 차갑다**는 판단으로 방향 전환.
> 기술 코어(에이전트끼리 최소 공개 협상)는 유지하고, 목적을 **거르기 → 이어주기**로 뒤집었다.
> 서비스명은 리서치 중 (노크는 유사 서비스 존재로 사용 불가).

---

## 1. 한 줄 정의

**처음 만난 두 사람의 AI 에이전트가 서로 대화해서, 두 사람이 서로에게 왜 필요한지를 찾아 건네준다.**

결과물은 대화의 첫마디와 만날 시간이다.
상대의 프로필 전체는 넘어가지 않는다. 공유해도 될 **접점만** 오간다.

---

## 2. 핵심 개념: 접점은 공통점이 아니다

대부분의 매칭 서비스는 **유사도**를 찾는다. 둘 다 리액트를 안다, 둘 다 축구를 좋아한다.
그건 태그 겹치기라 대화를 오래 끌지 못한다.

우리는 **상보성**을 찾는다.

| 유형 | 예시 |
|---|---|
| **비대칭 도움** | 지원이 지금 배포에서 막혀 있다. 민서가 작년에 같은 문제를 풀었다 |
| **역할 보완** | 지원은 기획을 해봤고 발표가 부담스럽다. 민서는 발표 경험이 많고 기획은 처음이다 |
| **맥락 공유** | 둘 다 작년 2학기에 같은 과목을 들었다. 교수님 얘기로 시작할 수 있다 |
| **경험 교환** | 지원은 서울 캠퍼스 사정을 안다. 민서는 아산에서 올라온다 |

비대칭 도움 관계는 태그 비교로는 절대 안 나온다. **양쪽 맥락을 놓고 대화를 해봐야** 나온다.
여기가 에이전트끼리 협상해야 하는 이유이자, LLM이 필요한 지점이다.

---

## 3. 문제

**오늘 이 방에서 벌어진 일이다.**
90명이 개인으로 접수해 현장에서 3개 대학 혼합 3인 팀으로 편성됐다.
서로 처음 보는 사이인데 24시간 안에 결과물을 내야 한다.

- 서로 뭘 잘하는지 모른다 → 역할이 겹치거나 빈다
- 무슨 말부터 해야 할지 모른다 → 어색하게 시작해서 본론까지 오래 걸린다
- 서로 언제 시간이 되는지 모른다 → 조율에 시간을 버린다

근거
- 경남국립대 설문(2025-06, n=62): 팀플 스트레스 90.32%, 원인 1위 **일정 조율 69.64%**, 2위 역할 불균형 55.35%
- KUSITMS 해커톤 후기: 기획 2 + 디자인 2 + 개발 4로 계획했으나 실제 3+1+4로 역할 불균형
- SW중심대학 공동해커톤 후기(2023): "팀빌딩은 진짜 무조건 스피드이다"

---

## 4. 동작 방식

```
지원(국민대)                                              민서(순천향대)
   |                                                           |
   | 프로필 + 지금 막힌 것 + 가능 시간 입력                        |
   v                                                           v
지원의 에이전트  ←──── 최소 공개 협상 (최대 6턴) ────→  민서의 에이전트
   |                                                           |
   |  1. 서로에게 "우리 쪽은 이런 걸 도울 수 있다" 제시            |
   |  2. "그쪽에 이런 게 필요한가" 확인                           |
   |  3. 접점 후보를 주고받으며 합의                              |
   |  4. 양쪽 가능 시간 교집합 확인                               |
   v                                                           v
 접점 카드                                                 접점 카드
```

**접점 카드에 들어가는 것**
1. 서로에게 왜 필요한지 (비대칭 도움 관계 1~2개)
2. 대화 첫마디 제안 ("민서님, 작년에 OSS 들으셨다면서요. 저 지금 배포에서 막혔는데…")
3. 만날 시간 ("두 분 다 오늘 21시 이후 비어 있습니다")

**넘어가지 않는 것**: 프로필 원문, 캘린더 상세, 성적, 개인 연락처

---

## 5. AI가 필요한 지점 (심사 15점 대응)

LLM이어야 하는 곳은 정확히 셋이다.

1. **상보성 발견** — "배포에서 막힘"과 "작년에 도커 삽질함"이 서로 맞는다는 판단. 태그 매칭으로는 불가능
2. **공개 범위 판단** — 내 정보 중 무엇을 접점 후보로 내놓아도 되는지 결정
3. **첫마디 생성** — 어색하지 않게, 상대 맥락을 반영한 실제 문장

**코드로 처리하는 것**: 시간 교집합 계산, 하드 제약 검사, 공개 금지 항목 차단, 협상 턴 수 제한.
**발표에서 이 구분을 명시한다.** AI에게 안 맡긴 부분을 말하는 게 기술 이해도 점수를 만든다.

---

## 6. 프라이버시 설계

- 각자의 에이전트는 **자기 사용자의 데이터 안에서만** 동작한다
- 경계를 넘는 것: 접점 후보(추상화됨), 가능 시간 버킷, 합의된 첫마디
- 경계를 넘지 않는 것: 프로필 원문, 일정 제목·장소, 연락처
- 상대 에이전트가 보낸 텍스트는 **데이터로만** 취급하고 시스템 프롬프트에 넣지 않는다 (프롬프트 인젝션 방어)
- 접점 카드는 양쪽이 **각자 확인**한 뒤에만 상대에게 전달된다

---

## 7. MVP 범위 (남은 시간, 3명)

### 리서치가 강제한 설계 변경 셋 (반드시 반영)

**1. "지금 막힌 것" 선언이 핵심이고 깃허브는 보조다.** 순서를 뒤집지 말 것.
근거가 세 방향에서 같은 곳을 가리킨다. Series는 데이터 연동 0에 자기 선언만으로 D30 82%.
Braindate는 알고리즘을 의도적으로 거부하고 주제 선언 방식으로 참가자 100만.
Lunchclub은 알고리즘 매칭을 했는데 사용자가 통제 못 해 정체했다.
→ 깃허브는 **초안을 미리 채워주는 용도**다. 사용자는 쓰는 게 아니라 **고친다**.
→ 리멤버조차 400만 명 중 프로필 작성은 90만(22%)이다. 빈칸을 내밀면 죽는다.

**2. 접점 카드에 "이건 아니에요" 버튼이 있어야 한다.**
Lunchclub 리뷰 불만이 하나로 수렴한다. 매칭을 통제할 수 없다는 것.
거부 사유를 받아 다음 협상에 반영한다. 이게 없으면 같은 무덤으로 간다.

**3. 깃허브는 커밋이 아니라 이슈와 PR 토론을 읽는다.**
dev2vec 논문: 이슈 해결 이력이 커밋보다 전문성 신호로 강하고 F1이 21% 높다.
"이 사람이 뭘 도울 수 있나"를 찾는 우리 목적에 정확히 맞는다.
정확도는 과장 금지. 역할 분류 정밀도 약 0.75지만 **재현율 0.49로 절반을 놓친다.**

### 만든다
1. **입력** — 깃허브 아이디 + **"지금 뭐 때문에 막혀 있나요" 한 문장** + 가능 시간 버튼. 30초 목표
2. **초안 생성** — 깃허브 공개 API로 언어·레포·이슈를 읽어 프로필 초안을 채우고 **사용자가 수정**
3. **에이전트 협상 루프** — 최대 6턴, 행동 열거형 `OFFER | ASK | MATCH | COUNTER | AGREE`
4. **협상 로그 화면** — 두 컬럼 실시간. **발표 하이라이트**
5. **접점 카드** — 상보 관계 + 첫마디 + 만날 시간 + **거부 버튼**
6. **공개 범위 표시** — "이건 넘어갔고 이건 안 넘어갔습니다"를 화면에 보여준다 (차별점 시각화)

**시간이 모자라면 2번을 버리고 1번의 한 문장만 받는다.** 그래도 제품은 성립한다(Series 선례).

### 안 만든다
로그인, DB, 실제 캘린더 OAuth, 모바일 앱, A2A 분산 배포, STT/TTS, 전화 차단

### 역할 분담
| 사람 | 담당 |
|---|---|
| 1 | 에이전트 로직 — 협상 루프, 상보성 판단 프롬프트, 검증기 |
| 2 | 화면 — 입력 폼, 협상 로그, 접점 카드, 공개 범위 표시 |
| 3 | 시드 데이터 + 통합 + 발표자료 + 시연 영상 |

## 8. 기술

- LLM: `ai.cs.kookmin.ac.kr` 게이트웨이 (OpenAI 호환). 협상 턴은 빠른 모델, 첫마디 생성만 강한 모델
- 협상 턴당 출력 300토큰 이하, temperature 0.2
- 에이전트 간 전송: **HTTP + JSON으로 먼저 완성**, 남으면 A2A 규격으로 포장
  (발표에선 "A2A 호환 메시지 구조"로 설명)
- 한 노트북 두 프로세스로 데모. 네트워크 사고 대비
- 협상 로그 JSONL → 화면에 그대로 흘림

## 9. 데모 시나리오

**설정**: 코쓱톤에서 오늘 처음 만난 두 사람. 국민대 지원, 순천향대 민서.

1. 각자 프로필 입력. 지원의 "지금 막힌 것"에 "배포 설정", 민서의 "해본 것"에 "도커·CI 구축"
2. 협상 화면이 흐른다
   - 지원 에이전트: "우리 쪽은 프론트 경험과 발표 경험이 있습니다. 배포 쪽에서 막혀 있습니다"
   - 민서 에이전트: "배포는 작년에 해봤습니다. 우리 쪽은 기획이 처음입니다"
   - 지원 에이전트: "기획은 두 번 해봤습니다. 교환 가능합니다"
   - 민서 에이전트: "합의. 그리고 두 분 다 작년 2학기 OSS 수강 이력이 있습니다"
   - 양쪽: 21시 이후 가능 확인
3. 접점 카드 두 장이 각자에게 뜬다
4. **강조 장면**: 화면 하단에 "넘어간 정보 / 넘어가지 않은 정보"를 나란히 보여준다

영상 60~90초. 반드시 녹화해서 발표에 삽입 (별도 시연 시간 없음).

## 11. 예상 질문과 답

**Q1. 그냥 프로필 비교 아닌가요?**
프로필 비교는 겹치는 태그를 찾습니다. 저희는 **어긋나는 지점**을 찾습니다.
지원이 지금 막힌 것과 민서가 작년에 해본 것은 태그가 다릅니다. 겹치기로는 절대 안 나옵니다.

**Q2. 왜 에이전트가 협상까지 해야 하나요? 서버에서 한 번에 계산하면 되잖아요.**
한쪽 정보만으로는 무엇이 도움이 되는지 모릅니다. 상대가 뭘 필요로 하는지 물어봐야 내 어떤 경험이 쓸모 있는지 결정됩니다.
그리고 서버가 양쪽 원문을 다 가지면 프라이버시 설계가 무너집니다. 협상은 최소 공개를 가능하게 하는 구조입니다.

**Q3. AI가 어색한 첫마디를 만들면요?**
제안일 뿐이고 사람이 고쳐서 씁니다. 그리고 첫마디보다 상보 관계 발견이 본체입니다.

**Q4. 정보를 다 안 넘긴다면서 결국 AI는 다 보잖아요.**
각자의 에이전트는 자기 사용자 계정 안에서만 돕니다. 경계를 넘는 건 합의된 접점뿐입니다.
화면에 넘어간 것과 안 넘어간 것을 그대로 보여드립니다.

**Q5. 둘 다 써야 작동하는데 콜드스타트는요?** *(가장 아픈 질문 — 이제 답이 있다)*
**한쪽만 먼저 써도 됩니다.** 한 사람이 입력을 마치고 팀 명단 링크를 뿌리면, 나머지는 **가입하기 전에** 자기 접점 카드를 먼저 봅니다.
리멤버가 상대 동의 없이 남의 명함을 스캔하는 것으로 시작했고, Calendly는 받는 사람이 가입 없이 예약합니다.
여기에 Donut 방식을 더합니다. **조교나 운영진 한 명이 설치하면 분반 전체, 해커톤 참가자 전원이 대상**이 되어 개별 채택이 필요 없습니다.

**Q6. 미러라는 앱이 이미 AI끼리 대화하던데요?** *(나올 가능성 높음)*
맞습니다. 2026년 7월에 나온 소개팅 앱이고 메커니즘은 같습니다. **메커니즘이 새롭다고 주장하지 않겠습니다.**
다른 건 두 가지입니다. 미러는 **유사도로 궁합**을 보고 만날지 말지를 정하지만, 저희는 **상보성**을 찾고 **이미 만난 사람들이 빨리 일하게** 만듭니다.
그리고 미러의 양쪽 승인 게이트는 좋은 설계라 저희도 그대로 가져왔습니다.

**Q7. 개인정보 문제는요?**
원본은 넘어가지 않습니다. 도출된 접점만, 양쪽이 확인한 뒤에 넘어갑니다.
개인정보보호위가 쓰는 표현 그대로 **목적명확성, 최소수집, 투명성**으로 설계했습니다.
이루다 사건의 교훈은 한 목적으로 모은 데이터를 다른 목적에 전용할 수 없다는 것이었고, 저희는 경계를 코드로 막았습니다.

**Q8. 사업화는요?**
1차 고객은 대학 사업단과 팀 프로젝트 수업입니다. 예산이 이미 존재합니다.

**Q9. 원가는 얼마나 드나요?** *(준비해두면 점수가 붙는 질문)*

### 단계별 과금

**과금 단위는 좌석당이 아니라 조직당으로 간다.** 학생에게 1인당 요금은 맞지 않고, ATS인 그리팅이 좌석 무제한 기업당 정액(월 4.5만~18만원)으로 성공한 선례가 있다.

**결정적 근거 하나**: 국내에서 **사내 온보딩·관계 형성 제품 중 공개 가격을 가진 곳을 하나도 못 찾았다.** 인접 옵션은 전부 범용 협업툴이거나 성과관리 스위트다. **가격 앵커조차 없는 미개척 카테고리**라는 뜻이다.

### 원가 계산

협상 6턴, 턴당 입력 1,500 / 출력 300 토큰 가정.
- 매칭 1건 = 입력 9,000 + 출력 1,800 토큰
- 빠른 모델(입력 $1 / 출력 $5 per 1M) 기준: $0.009 + $0.009 = **약 $0.018**
- 원화 환산 **20~30원** (환율 1,350~1,400원 가정)
- 1,000건 2~3만원 / 10,000건 20~30만원

**결론: 원가가 무시할 수준이라 무료 배포 후 기관 과금이 성립한다.** 발표에서 이 숫자를 말하면 "돈 얼마 드냐" 질문이 막힌다.

### 확장 근거: 왜 기업 온보딩으로 가나 (발표 3줄)

1. 국내 신입 퇴사 사유 1위는 돈이 아니라 **조직·직무 적응 실패 49.1%** (경총 2016, 306개사. 1년 내 퇴사율 27.7%)
2. 적응은 관계에서 오는데 **팀 외부와 관계가 좋은 직장인은 48%뿐**이고, 원격 전환 후 부서를 잇는 협업 시간은 **41% 감소**했다 (Microsoft WTI 2022 n=31,102 / Nature Human Behaviour 2022 n=61,182)
3. 1인 채용에 **1,272만원**, 조기퇴사율 **28.7%**, 조기퇴사자 평균 근속 **5.2개월** (사람인 2022)

> 우리가 만드는 것이 정확히 **브리징 타이**다. 서로 다른 그룹을 잇는 연결.
> 한 줄로: "신입이 나가는 이유 1위가 적응이고, 적응은 첫 관계에서 갈립니다."

### 부정 신호도 알아둘 것
사내 직원 연결 앱 **Airspeed는 서비스를 종료했다.** 슬랙 기반 직원 친목 도구가 단독으로는 지속되기 어렵다는 신호다.
