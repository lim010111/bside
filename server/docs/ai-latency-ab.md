# 변경 전후 AI 처리 시간 실측 — 2026-09-20

**실모델 비교에서 정상 완료된 요청의 중앙값은 후보 5명 25.6%, 20명 22.5%,
50명 24.1% 줄었다. 1명은 3.8%로 차이가 작았다.** 다만 20명 변경 후 3회 중 한 번은
JSON 오류로 5명 평가가 실패해, 정상 완료 비교는 해당 전후 한 쌍을 제외한 2쌍이다.
속도 개선과 출력 안정성·추천 품질은 구분해야 한다.

## 조건과 측정 경계

- 모델: `claude-haiku-4-5`, 기존에 설정된 게이트웨이.
- 변경 전: 커밋 `7e7f5c7`의 프롬프트 `042d9e7cf2358995`.
- 변경 후: 현재 `2026-09-20.3`, 프롬프트 `ff85b83b0d8db46e`.
- 양쪽 모두 배치 5명, 동시성 4, 출력 상한 4096, 온도 0.2, 시도 1회.
  요청 타임아웃 20초, 전체 타임아웃 45초도 동일하다.
- 후보 1·5·20·50명은 각 조건을 3회씩 측정했다. 전후 순서를 교차하고 후보 수 순서도
  반복마다 바꿨다. 양쪽 프롬프트를 동시에 호출해 서로의 속도를 방해하지 않았다.
- **입력 본문·후보 ID·순서는 한 비교 쌍 안에서 동일하다.** 로컬 Redis에서 매번 새
  쌍 캐시 키로 시작했으며 콜드 측정의 캐시 적중은 모두 0이었다.
- 양쪽 모두 현재 서버의 동일한 서비스·검증 코드를 사용하고 프롬프트만 교체했다.
  따라서 모델 출력 변경 효과를 비교하며, 중복 잠금 수정의 별도 성능 효과는 이 표에
  포함하지 않는다. 기존 긴 형식 응답과 새 압축 응답 모두 현재 서비스가 처리한다.
- 시간은 `recommend()` 호출부터 반환까지다. 외부 모델/네트워크, 배치 대기,
  원문 검증과 Redis 저장을 포함한다. HTTP 엔드포인트·최초 BLE 보고·화면 갱신은 제외한다.
  비스트리밍 경로라 첫 토큰 시간이나 모델 내부 판단 시간을 분리하지 않는다.
- 50명은 기존 합성 프로필 20개를 순환해 다른 ID로 확장했다. 긴 소개는 같은 합성
  문장을 반복해 필드당 약 480자까지 늘린 부하 사례다. 실제 행사 사용자 표본은 아니다.
- 실행: 한국 시각 **06:22:05–06:26:55**. 실제 모델 요청 104회, 논리 평가 32회,
  평가 후보 490건. 게이트웨이 자동 재시도는 없었다.

## 후보 수별 결과

**양쪽 모두 모든 후보의 판정이 완료된 비교 쌍**만 같은 반복끼리 묶은 중앙값이다.
`insufficient_evidence`는 완료된 판정에 포함하고 `failed`는 포함하지 않는다.
단축률은 `1 - 변경 후 중앙값 / 변경 전 중앙값`이다.

| 후보 | 정상 비교 쌍 | 변경 전 | 변경 후 | 절약 시간 | 단축률 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1명 | 3 | 2.604초 | 2.506초 | 0.098초 | 3.77% |
| 5명 | 3 | 8.662초 | 6.448초 | 2.214초 | 25.56% |
| 20명 | 2 | 8.874초 | 6.874초 | 2.000초 | 22.54% |
| 50명 | 3 | 25.673초 | 19.495초 | 6.178초 | 24.06% |

20명 세 번째 변경 후 실행은 7.917초에 반환했지만 5명은 `INVALID_JSON`이었다.
이 실행과 짝인 변경 전 실행을 함께 제외했다. 실패도 포함해 단순 반환 시간 중앙값을
구하면 20명은 **8.872초→7.297초, 17.76% 감소**다. 실패 후보의 재시도를 거쳐 모든
판정이 완료될 때까지의 시간은 측정하지 않았으므로, 이 실패 실행에 정상 완료 시간을
대입하거나 재시도 비용을 0으로 간주하지 않는다.

반복별 편차도 있다. 5명의 전후 쌍별 단축률은 16.28–27.99%, 20명의 정상 쌍은
8.60–33.94%, 50명은 17.87–25.55%다. 3회 이하 표본이며 장기 평균·p95·운영 보장값이 아니다.

전체 호출에서 제공자가 보고한 토큰을 합산했다. 실패 응답이 소비한 토큰도 포함한다.

| --- | ---: | ---: | ---: |
| 입력 토큰 | 154,392 | 169,940 | +10.07% |
| 출력 토큰 | 71,142 | 50,289 | -29.31% |
| 총 토큰 | 225,534 | 220,229 | -2.35% |

압축 형식 설명 때문에 입력은 늘었지만 출력이 줄었다. 이는 출력량 축소가 지연 개선에
기여했다는 해석과 일치한다. 후보 판단 내용도 달라지므로 출력 길이만의 인과 효과를
분리한 실험은 아니다. 총 토큰 감소율을 비용 감소율로 해석하지 않는다.

다음은 각 조건 **1회씩**의 추가 관찰이다.

| 시나리오 | 변경 전 | 변경 후 | 해석 |
| --- | ---: | ---: | --- |

## 오류와 추천 결과 변화

- 변경 전은 후보 245건 중 **1건 실패**: E06의 입력 내 지시문 후보에서 검증된 원문 근거가
  하나도 없어 `UNGROUNDED_REASON`으로 차단했다.
- 변경 후는 후보 245건 중 **5건 실패**: 20명 세 번째 실행의 한 배치가 JSON 배열/객체를
  닫지 않아 배치 전체가 `INVALID_JSON`이었다. 출력 상한에 따른 `OUTPUT_TRUNCATED`는
  아니었다. 실패를 성공으로 바꾸거나 잘린 JSON을 임의로 보완하지 않았다.
- 전체 논리 실행으로는 양쪽 모두 16회 중 1회에 후보 실패가 있었다. 표본이 작아
  장기 실패 확률이나 압축 형식이 오류를 유발했다는 인과 관계를 확정할 수 없다.
- 일부 근거의 인용 검증 실패는 전 조건 2구절, 후 조건 1구절이었다. 이때 다른 검증된
  근거가 있으면 평가는 유지되지만 알림 정책이 추가 제한한다.
- 20명 정상 비교에서도 상위 3명의 구성은 한 쌍에서 3명 모두 같고 다른 쌍에서는
  2명만 같았다. 근거 부족 판정·점수·의도 충돌 표시도 달라졌다.
  **새 모델 생성 결과의 품질과 판정이 완전히 동일하다고 결론 내릴 수 없다.**

이전 [압축 응답 재생](ai-latency-improvements.md)의 “점수·근거·판정 동일”은 이미 생성된
같은 답을 형식만 바꿔 서버에 넣었을 때의 무손실 확인이다. 이번처럼 모델에게 새로
생성시킨 답이 같다는 의미가 아니다.

캐시 재조회는 성공한 콜드 평가에 대해서만 수행했다. 중앙값은 전 조건 1.242ms,
후 조건 1.050ms이며 추가 모델 호출은 0건이다. 순수 캐시 적중에는 이미 초 단위
개선 여지가 없었다.

## 화면 전달 효과는 별도 계산

측정한 캐시 저장 시각에 기존 15초/변경 후 1초 조회 주기를 대입하면 다음과 같다.
최초 pending 응답을 0초로 두고 네트워크·렌더링 지연 0, 보이는 화면, 기존 방식은
지속적인 BLE 재관측을 가정한다. 정상 완료된 쌍만 사용한다.

| 후보 | 기존 주기에 실리는 시각 중앙값 | 변경 후 중앙값 |
| --- | ---: | ---: |
| 1명 | 15초 | 3초 |
| 5명 | 15초 | 7초 |
| 20명 | 15초 | 7.5초 |
| 50명 | 30초 | 20초 |

**이는 측정한 AI 시간을 이용한 조회 스케줄 계산이며 실기기 end-to-end 실측이 아니다.**
실제 새 조회는 HTTP 응답 후 1초를 기다리므로 왕복 지연도 누적되고, 최초 BLE 보고 주기와
화면이 숨겨진 시간도 별도로 영향을 준다. 기존 방식은 재관측이 없으면 위 시각에도
결과가 도착하지 않을 수 있다.

## 재현과 산출물

- [전체 원본](../evals/reports/latency-ab-live-2026-09-20.json): 입력, 두 시스템 프롬프트,
  배치별 원문 응답·시각, 정규화 결과, 토큰, 실패와 모든 실행의 요약.
- [분석 결과](../evals/reports/latency-ab-analysis-2026-09-20.json): 정상 전후 쌍,
  전체 집계, 기존 품질 검사, 점수·상위 순위 변화, 조회 스케줄 계산.
- [실행 코드](../evals/bench/latency_ab.py), [추가 호출 없는 분석 코드](../evals/bench/analyze_latency_ab.mjs).

```sh
cd server
# 새 모델 호출 없이 저장 결과 분석
node evals/bench/analyze_latency_ab.mjs \
  evals/reports/latency-ab-live-2026-09-20.json \
  evals/reports/latency-ab-analysis-2026-09-20.json

# 실호출 재측정에는 별도 가용 예산과 격리된 로컬 Redis가 필요하다.
uv run python evals/bench/latency_ab.py --live \
  --redis-url redis://127.0.0.1:<테스트포트>/15 \
  --output evals/reports/<새파일>.json --max-new-calls 104
```

사용자의 추가 실측 요청에 따라 이번 작업의 호출 한도를 104건으로 잡았다. 기존 장부의
241건(보수적 예약 포함)을 보존하고 cap을 345로 늘린 뒤, 실행 전 예약하고 실제 시도
104건으로 정산했다. 현재 장부는 **345/345**, 남은 0이다. 기존 호출 수를 지우거나
새 예산으로 숨기지 않았다. 제품 코드는 이 측정 중 변경하지 않았다.
