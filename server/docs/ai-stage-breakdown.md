# AI 지연의 작업별 분석 — 2026-09-20

> 개선 전 코드 `7e7f5c7`의 분석 기록이다. 이후 [개선 구현](ai-latency-improvements.md)과
> [실모델 시간 단축률 측정](ai-latency-ab.md)을 완료했다.

**서버의 주된 병목은 LLM 응답을 기다리는 구간이다. 점수·추천 이유·원문 근거를 한 번에
생성하므로 스코어링과 이유 작성의 시간을 개별 측정한 값은 없다. 긴 이유·근거 출력이
주요 비용일 가능성이 높고, 화면에서는 결과를 다시 조회하는 주기도 큰 지연 요인이다.**

현재 코드 `7e7f5c7`의 프롬프트 digest `042d9e7cf2358995`, inference digest
`527544c990f8e174`가 [최신 실측](../evals/reports/latency-live-2026-09-20.json)과
일치함을 확인했다. 이 문서는 기존 실측 재분석과 추가 오프라인 측정이다.
새 실모델 호출은 0건이며, 제품 코드는 변경하지 않았다.

**실제 호출 구조**

`캐시 조회 → 5명씩 배치, 최대 4개 동시 실행 → LLM의 전체 JSON 수신 → JSON/스키마 검증
→ 근거 인용 확인 → 캐시 저장 → 점수순 정렬·알림 대상 판정`

[평가 서비스](../app/ai/service.py)의 `_evaluate_batch()`가 게이트웨이를 한 번 호출한다.
[프롬프트](../app/ai/prompt.py)는 후보마다 `score`, `reason`, `evidence`, 상태와 의도 충돌
여부를 함께 요구한다. 별도의 임베딩·벡터 검색·reranker·이유 작성용 두 번째 모델 호출은
이 경로에 없다. 점수는 모델이 결정하고 Python은 받은 점수로 정렬한다.
[게이트웨이](../app/ai/gateway.py)는 스트리밍 없이 전체 응답을 받는다.
JSON에서 score가 reason보다 먼저 나와도 현재 구현에서는 점수를 먼저 사용할 수 없다.

Haiku 4.5, 후보 수별 3회, 매번 빈 로컬 Redis 캐시. 네트워크와 모델을 포함한
`recommend()` 전체 시간이며 HTTP 관측 API·BLE·화면 갱신은 제외한다.

| 후보 수 | 최초 평가 중앙값 | 입력 토큰/회 | 출력 토큰/회 | 모델 호출 |
| --- | ---: | ---: | ---: | ---: |
| 1명 | 2.460초 | 2,539 | 322 | 1 |
| 5명 | 8.658초 | 2,894 | 1,472–1,650 | 1 |
| 20명 | 9.051초 | 11,553 | 5,906–6,075 | 4개 병렬 |

1명에서 5명으로 늘면 입력은 14% 증가하지만 출력 중앙값은 약 5배, 시간은 약 3.5배다.
이는 응답 생성량이 중요한 병목이라는 단서다. 후보별 판단량도 함께 증가하므로
출력 길이만의 인과 효과로 해석하지 않는다. 20명은 네 배치가 병렬이라 5명과 시간이 비슷하다.
20명의 전체 출력 토큰을 9초로 나눈 값을 단일 요청의 토큰 생성 속도로 해석해서도 안 된다.

Anthropic도 입력·출력 길이 축소와 스트리밍을 지연 개선 수단으로 설명한다.
다만 이는 일반 지침이며 이 프로젝트 게이트웨이의 시간 분해를 대신하지 않는다.
[공식 지연 문서](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency).

**추천 이유 외에 원문 근거 출력도 크다**

이전 프롬프트 `32db67109c375cf1`의 저장된 Haiku 응답 7사례·33명을 재분석했다.
24명은 평가 완료, 9명은 근거 부족이다. 모델 출력 필드만 복원한 compact JSON의
`key:value` 문자 수에서 evidence는 **49.72%**, reason은 **25.52%**, score는 **3.65%**였다.
나머지는 ID·상태·의도 충돌 필드다. 배열/응답 외곽 구조와 필드 사이 쉼표는 제외했다.
이유가 있는 24명의 이유 길이 중앙값은 99.5자, 개별 근거 구절의 중앙값은 30자였다.

**이는 이전 응답의 문자 비중이며 현재 응답의 토큰 비중이나 소요 시간 비중이 아니다.**
최신 9회 실측은 토큰 합계만 저장해 현재 프롬프트의 필드별 원문 비중은 알 수 없다.
또 점수 숫자가 짧아도 점수를 결정하는 모델 판단이 저렴하다고 증명되지는 않는다.
현재도 양쪽 자기소개·교류 의도의 근거를 출력하도록 요구하므로, 최적화 실험에서는
reason과 evidence를 함께 비교할 이유가 충분하다.

기존 E01의 실제 모델 응답과 입력 5명을 ID를 달리해 네 번 복제하고, 현재 서비스에

**화면 전달과 여러 사용자 환경은 별도 병목이다**

[네이티브 서비스](../../android/app/src/main/java/app/bside/discovery/DiscoveryService.kt)와
[웹 컨트롤러](../../web/src/discovery-controller.js)에 15초 주기가 있다.
네이티브 보고만 있고 연속 재관측·빠른 네트워크라는 단순 조건에서는,
AI가 약 9초에 끝나도 첫 pending 응답 후 다음 보고인 약 15초 뒤에 추천이 전달된다.
최초 BLE 수신부터는 약 15–30초가 될 수 있다. 이는 코드에 따른 예시이며 실기기 실측이나
상한이 아니다. 웹 주기·수동 새로고침이 겹치면 더 빨라질 수도 있다.
현재 코드에는 FCM 추천 알림 경로도 있으나, 푸시가 목록의 점수·이유 데이터를 갱신하지는 않는다.
따라서 이전 지연 보고서의 “추천 시스템 알림 미구현” 문구는 현재 코드에 적용하지 않는다.

여러 사용자는 서비스 인스턴스의 동시 실행 4개를 공유해 모델 호출 전 큐 대기가 생긴다.
의도 수정 후에도 이전 작업의 잠금이 남는 문제와 재관측이 없으면 결과를 조회하지 않는
문제도 현재 코드에 남아 있다. 이때 오래 보이는 pending을 모델 생성 시간으로 오인하면 안 된다.
[기존 모의 부하·상태 전달 검증](ai-latency-review.md).

**우선 비교할 개선안**

1. 화면에서 pending 결과를 더 일찍 갱신하도록 전달 경로를 개선한다. 모델이 빨라져도 같은
   15초 조회에 실리면 사용자 체감이 바뀌지 않을 수 있다.
2. 같은 입력으로 현재 출력, reason 생략, evidence 축약, 둘 다 축약을 비교한다.
   첫 토큰 시간·전체 응답 시간·출력 토큰과 추천 순위/근거 품질을 함께 측정한다.
   근거를 없애거나 이유를 상위 후보에게만 생성하려면 현재 검증·응답 계약도 함께 설계해야 한다.
3. 큐 진입/실행 시각을 추가해 사용자 증가에 따른 대기를 모델 처리와 분리한다.

최신 실측에는 배치별 첫 토큰·완료 시각 및 게이트웨이 내부 큐 정보가 없다.
따라서 현재 확정할 수 있는 결론은 **외부 AI 응답 대기가 지배적이고 로컬 정렬은 미미하다**는
것이다. **추천 이유·근거 생성이 주요 원인이라는 판단은 유력한 가설**이며, 스코어링과의
정확한 시간 분해는 통제된 출력 변형 실험이 필요하다. 기존 live 장부는 cap 240에
예약 포함 241이므로 이번 조사에서는 추가 실모델 호출을 실행하지 않았다.
