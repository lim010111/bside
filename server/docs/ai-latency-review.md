# AI 분류·추천 지연 검증 — 2026-09-20

> 이 문서는 개선 전 구현의 진단 기록이다. 현재 변경과 후속 실측은
> [AI 지연 개선](ai-latency-improvements.md)과 [실모델 전후 비교](ai-latency-ab.md)를 따른다.

**현재 Haiku의 20명 첫 평가는 중앙값 9.05초이며 기존 5초 목표에 미달한다.**
몇 분 이상 머무는 상대를 대상으로 목록을 먼저 보고 대화하는 MVP에는 조건부로 수용할 수
있지만, 의도 변경 시연·앱 밖 자동 추천·여러 사용자가 동시에 들어오는 상황은 현재 구현의
결함과 미완성 기능 때문에 통과로 판정할 수 없다. 모델 계산 외에 결과 전달 시간이 크다.

검토 기준은 `af74f33`의 코드와 [시연](../../spec/scenario.md),
[제품 요구](../../spec/PRD.md), [AI-D5 검증 목표](../../docs/validation.md)다.
일부 README의 “AI API 미연결” 문구는 현재 코드와 다르다. 관측 API는 이미 백그라운드 평가와
Redis 캐시를 사용하며, [배포 기록](../../docs/deployment.md)은 실기기의 `pending → ready`를
기록했다. 이번에는 연결된 Android 기기가 없어 기기 측 시간을 다시 재지는 못했다.

5초 목표 달성을 뜻하지 않는다. 5명과 20명이 비슷한 것은 20명을 네 배치로 병렬 처리하기 때문이다.

## 사용자가 기다리는 시간

```text
BLE 최초 수신
  → 다음 관측 보고까지 대기
  → 목록 + pending 반환 / 서버 AI 작업 시작
  → AI 결과를 Redis에 저장
  → 다음 관측 보고에서 ready 전달
  → 목록 및 상세 화면 반영
```

[네이티브 서비스](../../android/app/src/main/java/app/bside/discovery/DiscoveryService.kt)는
매 처리 완료 후 15초를 기다려 보고한다. 화면에서도
[15초 refresh](../../web/src/discovery-controller.js)가 `refreshObservations()`를 부른다.
두 주기가 겹칠 수 있어 하나의 정확한 고정 주기로 보장되지는 않는다. 수동 새로고침·주기 위상에
따라 더 빨라질 수도 있다.

연속 관측이 있고 네트워크가 빠르며 네이티브의 15초 주기로만 전달되는 단순 모델에서는:

- 최초 BLE 수신 → 첫 목록: 약 0–15초 + 요청 시간.
- 첫 pending 응답 → 추천 목록: AI가 15초 안에 끝나면 다음 보고인 약 15초 뒤.
- 최초 BLE 수신 → 추천 목록: **약 15–30초 + 네트워크·스케줄링 시간**.

이는 코드에서 계산한 예시이며 실기기 측정 범위나 상한이 아니다. 발견 이전의 BLE 탐지 지연,
재관측 누락, 느린 네트워크, 재시도와 큐 대기는 별도다. 모델을 9초에서 4초로 줄여도 두 결과가
모두 다음 15초 보고에 실리면 체감은 그대로일 수 있다.

`sweepAndReport()`는 새로 들은 ID가 없으면 요청 자체를 하지 않는다. 따라서 평가가 끝났어도
재관측이 없으면 추천 결과를 다시 가져오지 않는다. 추천 결과 조회/전달을 근접 관측 갱신과
분리해야 한다. 결과 조회가 상대를 새로 관측한 것으로 처리되어 첫 메시지 권한을 연장해서는 안 된다.

| 실패가 계속 준비 중으로 표시 | timeout 주입 후 다음 poll에도 `pending`; 모듈의 `FAILED`가 저장되지 않아 API에서 읽을 수 없다 | 실패 상태·재시도 가능 시각을 별도 보관하고 제한된 재시도/backoff 제공 |
| 추천 도착 후 상세가 갱신되지 않음 | native `ready` 이벤트 뒤 목록은 `ready`, 열어 둔 상세는 `pending`; `refreshAll()` 뒤에야 상세가 `ready` | 관측 이벤트 수신 시 현재 상세도 같은 최신 항목으로 반영 |
| AI deadline이 목록 캐시 읽기를 보호하지 않음 | AI 전체 deadline을 20ms로 두고 캐시 get을 120ms 지연시키자 `annotate()`가 120ms 기다렸다 | 목록 응답의 캐시 조회에 별도 짧은 대기 예산 적용 |

실제 Redis 클라이언트에는 소켓 timeout 2초가 있다. 마지막 재현이 운영에서 무조건 무한 대기를
뜻하는 것은 아니다. **AI의 전체 deadline과 즉시 목록 반환은 별개의 경계**라는 뜻이다.

의도 변경은 [시연 3단계](../../spec/scenario.md)에 직접 영향을 준다. 이전 작업이 시작된 시점을
기준으로 잠금이 만료될 때까지 기다린 뒤, 다음 보고·새 AI 평가·후속 보고를 더 거칠 수 있다.
“의도 수정 후 9초”로 설명하면 실제보다 짧게 약속하게 된다.

위 제품 동작은 이번 검증에서 수정하지 않았으며 후속 수정 대상이다.

## 여러 사용자가 함께 있을 때

“조회자 한 명의 후보 20명”은 “사용자 20명이 동시에 주변을 평가”하는 부하와 다르다.
동시성 4는 `RecommendationService` 인스턴스 전체가 공유한다. 단일 워커에서 20명이 각자
나머지 19명을 평가하면 **380개 방향별 평가, 최대 80개 배치 호출**이 필요하다.
반대 방향은 조회 의도가 달라 같은 캐시 결과로 대신할 수 없다.

이를 현재 코드에 **배치당 고정 9초라는 가정**으로 주입하고 시간을 50배 빠르게 돌렸다.
실제 gateway 동시 부하 측정이 아니며, 마지막 4명 배치에도 같은 9초를 적용한 가상 조건이다.

| 동시 조회자 | 조회자당 후보 | 현재 큐/deadline 동작 |
| --- | ---: | --- |
| 2명 | 19명 | 약 9초·18초에 해당하는 시간에 완료, 실패 0/38 |
| 5명 | 19명 | 마지막 요청이 45초 deadline에 걸림, 실패 19/95 |
| 20명 | 19명 | 4명의 평가만 완료, 나머지 후보 실패 304/380 |

모의 스케줄링/취소 오버헤드가 있어 환산값이 45초를 조금 넘는다. 실제 배치 시간·워커 수·
호출 제한에 따라 결과는 달라진다. `4 / 9 ≈ 0.44배치/초`, `80 × 9 / 4 ≈ 180초`는
대기 제한이 없다면 모든 작업을 소화하는 데 필요한 시간의 단순 추정이다.

워커를 늘리면 이 인스턴스별 제한도 늘어 gateway 요청량이 증가한다. 큐/동시성 숫자만
높이는 것을 검증된 해결책으로 삼을 수 없다. 진행 중 중복 억제, 오래된 작업 취소,
조회자 간 공정한 배치 처리, 전체 호출 제한과 queue wait 지표가 필요하다.

캐시는 15분 뒤 만료한다. 지속 ON으로 같은 사람들이 함께 머물러도 재평가 비용이 발생한다.
캐시 적중 결과와 신규 상대·프로필 변경·캐시 만료 후 cold 비율을 나누어 장시간 측정해야 한다.

## 시나리오와 일상 사용 판정

| 상황 | 판정 |
| --- | --- |
| Android 두 대, 앱을 열고 자기소개를 본 뒤 채팅 | **조건부 적합.** 상대 1명의 모델 평가는 약 2.5초이고 목록/채팅은 AI 완료를 기다리지 않는다. 추천이 보이는 시점은 전달 주기가 좌우한다 |
| 같은 소개에서 의도만 바꾸어 추천 변화 시연 | **현재 보완 필요.** 버전 없는 잠금과 상세 갱신 문제를 먼저 해결해야 한다 |
| 카페·스터디·모임에서 몇 분 이상 머물며 앱 사용 | **MVP 지연은 수용 가능하다는 가설.** 목록이 먼저 보이면 약 15–30초 전달 예시가 교류 기회를 반드시 없애지는 않는다. 사용자 관찰로 확인해야 한다 |
| 길거리·엘리베이터의 수초 스침 | **적합하지 않음.** 탐지·보고·AI·다음 전달 전에 헤어질 수 있으며 원래 MVP 보장 범위 밖이다 |
| 휴대폰을 잠그고 적합한 상대 알림을 기다림 | **현재 미충족.** 발견 ON 안내 외 추천 시스템 알림이 구현되지 않았다 |
| 여러 사람이 동시에 입장, BLE 후보 집합이 자주 바뀜 | **통과 근거 부족, 병목 재현.** 중복 작업과 공유 큐의 deadline 소진 가능성이 있다 |
| 이동통신 불안정·AI timeout | **목록/채팅 분리 방향은 적절하나 추천 상태는 부적절.** 실패를 계속 준비 중으로 안내할 수 있다 |

Android는 제조사 데이터 필터와 foreground service를 사용하고 있으므로 단순히 “화면이 꺼지면
항상 스캔이 멈춘다”고 단정하지 않는다. 공식 문서는 무필터 스캔의 화면 꺼짐 제약을 구분하며,
프로세스 생존에 의존하는 callback과 프로세스를 깨울 수 있는 PendingIntent 경로도 구분한다.
현재 코드의 `DiscoveryHolder` 상태는 프로세스 메모리에 있으므로 프로세스 종료/서비스 재시작까지
지속 발견이 검증된 것은 아니다.
[BluetoothLeScanner](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeScanner),
[백그라운드 BLE 공식 안내](https://developer.android.com/develop/connectivity/bluetooth/ble/background).

일상에서는 추천 품질·알림 피로·배터리도 별도로 검증해야 한다. 이번 개발/협업 중심 fixture로
“산책 상대”, “가벼운 대화”, “지금은 집중하고 싶음” 같은 일상 의도를 검증했다고 할 수 없다.
신규 일상 사례와 실제 사용자 기대값, 30–60분 화면 켜짐/꺼짐, 장소 이동, 네트워크 단절,
중복 알림·이미 떠난 상대 알림을 추가 실험 대상으로 둔다.

## 우선순위와 다음 측정

1. 의도 변경 잠금, 실패 상태, 상세 갱신을 먼저 고친다. 의도 변경 시연의 예측 가능성을 회복한다.
2. 추천 완료 전달을 15초 재관측과 분리한다. 화면을 볼 때 pending 결과만 짧게 재조회하거나
   완료 이벤트를 전달한다. 백그라운드 추천 알림에는 참여·관측·입력 버전 재확인과 중복 억제가 필요하다.
3. 동일 쌍 작업 공유와 큐 대기를 다룬 뒤, 여러 조회자 부하를 실제 gateway에서 제한된 예산으로 측정한다.
4. 그 후 프롬프트/출력 길이 등을 최적화하고 새 품질 사례로 재평가한다. 과거 배치 2 실험은
   5.6초로 빨라졌지만 판정이 바뀌고 토큰이 늘었으므로 속도만 보고 채택하지 않는다.

기존 **20명 추천 갱신 5초 목표는 유지된 미달 목표**다. 이번 검토가 그 목표를 15초나 30초로
완화하는 제품 결정은 아니다. 다음에는 BLE 최초 수신, 서버 관측 수신, 큐 진입/실행,
첫/전체 결과 저장, native 수신, 목록/상세 표시, 알림 게시를 각각 타임스탬프로 남긴다.
최초 발견과 의도 변경을 구분하고 충분한 반복으로 p50/p95·실패율·캐시 적중률을 측정한다.

## 검증 실행과 테스트 격리 수정

실모델 측정은 18개 배치 호출이었다. 기존 장부 208건에서 계획된 측정 후 226건이 됐다.
별도로 첫 전체 API 테스트 실행에서 기존 fixture가 `.env`의 실제 AI 설정을 읽어 2개 테스트가
실패했다(기대 `unavailable`, 실제 `pending`). 백그라운드 실제 gateway 호출이 발생했을
가능성이 있으며 그 실행은 호출 계측이 없어 실제 건수를 확정할 수 없다.

외부 호출을 모두 가로챈 오프라인 재현에서 최대 15개 배치가 예약될 수 있는 경로를 확인했다.
이를 **실제 호출로 단정하지 않고 보수적 15건 예약**으로 장부에 반영했다.
기존 cap 240은 변경하지 않았으며 예약 포함 합계 241, 남은 예산 -1이다. 추가 실모델 호출은
수행하지 않았다. [계측 한계·예약 근거](../evals/reports/latency-test-accounting-2026-09-20.json).

[테스트 fixture](../tests/conftest.py)를 고쳐 API용 설정과 독립적인 AI 설정도 명시적으로
미설정 상태로 주입했다. 추천 경계 테스트는 기존처럼 오프라인 gateway를 주입한다.
수정 뒤 같은 외부 호출 차단 계측을 적용해 **서버 276개 통과·skip 0, 실제 gateway 작업 예약 0개**,
웹 **46개 통과**를 확인했다. 제품 지연 결함이 이 테스트 통과로 해결된 것은 아니다.

```sh
# server/에서 별도로 띄운 로컬 임시 Redis를 지정한다. 운영 DB에 실행하지 않는다.
uv run --frozen python evals/bench/latency.py \
  --redis-url redis://127.0.0.1:<임시포트>/0 --repeats 1 --out /tmp/latency-offline.json
uv run --frozen python evals/bench/latency_probes.py \
  --redis-url redis://127.0.0.1:<임시포트>/0 --out /tmp/latency-probes.json
node evals/bench/latency_ui_probe.mjs
TEST_REDIS_URL=redis://127.0.0.1:<임시포트>/15 uv run --frozen pytest -q
```

`latency.py --live`는 실제 호출이며 기존 장부 cap과 실행 상한을 사전 확인한다. 현재 장부에서는
추가 실측이 차단된다. live 스크립트는 다른 유료 평가와 동시에 실행하지 않는다. 저장된 결과의
재분석이나 오프라인 재현에는 새 모델 호출이 필요하지 않다.
