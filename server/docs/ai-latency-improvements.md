# AI 추천 지연 개선 — 2026-09-20

모델이 생성하는 반복 JSON을 줄이고, 같은 평가의 중복 실행과 완료 후 화면 갱신 대기를
줄였다. 기존 [작업별 분석](ai-stage-breakdown.md)의 후속 구현이다. 제품 코드에 적용했으며
이 구현 단계에서는 배포·실기기 검증·새 프롬프트 실모델 측정을 수행하지 않았다.
이후 사용자 요청으로 [실모델 전후 비교](ai-latency-ab.md)를 완료했다. 정상 완료 비교에서
5·20·50명은 약 22~26% 빨라졌지만 JSON 오류와 판정 변화도 관찰돼 품질 동등성은 미확인이다.

## 적용한 변경

**모델 출력 압축.** 모델 응답은 후보마다 `id,t,s,r,c,e`를 사용한다. 근거는
`["vi", "원문 구절"]`처럼 출처 코드와 원문을 출력한다. 서버가 기존 평가 객체로 풀어
동일한 점수·원문 인용·의도 충돌·알림 검증을 수행한다. 원문을 지우거나 근거를 모델의
자기 확신으로 대체하지 않는다. 잘못된 코드·자료형·혼합 형식은 실패로 처리한다.
기존 긴 키 형식도 주입한 프롬프트와 저장 응답 재생을 위해 읽을 수 있다.

이유는 연결점 하나를 담은 한국어 존댓말 한 문장, 50~90자를 목표로 요청한다.
중요한 한계나 의도 충돌에는 두 문장을 허용한다. 완성된 문장을 서버에서 자르지 않는다.
프롬프트 버전은 `2026-09-20.3`, digest는 `ff85b83b0d8db46e`다. 캐시는 새 digest로
분리되므로 변경 직후에는 기존 추천 캐시를 재사용하지 않는다.

**후보별 중복 방지.** 작업 잠금을 후보 집합 전체에서 방향 있는 한 쌍으로 바꿨다.
조회자·후보 ID, 양쪽 프로필 버전과 내용 해시, 추론 설정이 작업의 식별자다.
서로 겹치는 목록은 이미 진행 중인 후보를 재평가하지 않고 새 후보만 처리한다.
완료·오류·취소 시 소유 토큰을 비교해 잠금을 해제하며, 만료 후 다른 작업이 얻은 잠금은
지우지 않는다. Redis 장애 시에도 같은 프로세스에서는 중복 실행을 막는다.
여러 프로세스 사이의 중복 방지는 Redis 가용성에 의존한다.

실패 결과는 API 어댑터가 15초간 보관해 `failed`로 보여준다. 빠른 조회가 매번 새 모델
요청을 만들지 않는다. 인메모리 캐시도 실제 TTL을 지키도록 수정했다.
알림 직전에는 양쪽 프로필 버전·발견 상태·관측 유효성을 다시 읽어 이미 낡은 평가의
알림을 걸러낸다. 이 검사는 읽기 후 상태가 바뀌는 경쟁까지 원자적으로 제거하지는 않는다.

**완료 결과의 독립 조회.** `POST /api/v1/discovery/recommendations/refresh`는 현재 화면의
사용자 ID 최대 50개를 받아 서버의 기존 관측과 최신 프로필을 확인한다. 추천 캐시만
읽으며 누락된 평가는 백그라운드로 예약한다. BLE ID 재제출과 새 관측은 필요 없다.
관측 시각과 대화 가능 시간을 갱신하지 않으며 미관측·만료·발견 OFF인 상대는 반환하지 않는다.

목록/상세가 보이고 평가가 진행 중이면 응답 후 약 1초 뒤 재조회한다. 완료된 배치는
즉시 표시하고 상세 화면도 함께 바꾼다. 네트워크 오류에는 최대 8초까지 간격을 늘리고,
`failed`만 남으면 15초 간격으로 재조회한다. 갱신 주기 하나는 60초까지이며 완료·발견 OFF·
화면 종료 시 멈춘다. 화면이 숨겨지면 빠른 HTTP 요청을 보내지 않는다.
새 관측·프로필 수정·앱 복귀는 새 주기를 시작한다. 취소되거나 이전 목록에 대한 응답은
새 목록을 덮어쓰지 못한다.

**대기 구간 관찰.** 배치별 후보 수, 세마포어 대기 `queue_ms`, 실행 `processing_ms`를
로그로 남긴다. 실행 시간에는 외부 응답·파싱·검증·캐시 저장이 포함된다. 첫 토큰 시간이나
모델 내부 판단 시간은 아니다. 프로필 본문과 모델 응답은 이 로그에 넣지 않는다.

## 확인한 효과와 시나리오

이전 Haiku 응답 7사례·33명을 같은 내용으로 재직렬화해 현재 서비스에서 재생했다.

| 지표 | 기존 긴 키 | 압축 형식 | 감소 |
| --- | ---: | ---: | ---: |
| JSON 문자 수 | 11,168 | 7,047 | 36.90% |
| UTF-8 바이트 | 17,142 | 13,021 | 24.04% |

점수·이유·원문 근거·상태·순위·알림 판정과 anomalies는 전 사례에서 같았다.
이는 저장된 정규화 결과에서 복원한 JSON이며 배치 외곽 구조를 포함한다. **토큰 감소율이나
소요 시간 감소율이 아니다.** 이유 길이를 바꾸지 않은 비교이므로 짧은 이유 지시의 추가
효과도 포함하지 않는다. [재생 수치](../evals/reports/compact-replay-2026-09-20.json).

| 시나리오 | 검증한 동작 |
| --- | --- |
| 후보 1·5·20·50명, 일부/전체 캐시 적중 | 누락된 쌍만 평가하고 모든 후보·연속 순위를 유지 |
| `{A}` 평가 중 `{A,B}` 관측 | A의 호출은 한 번, B는 별도로 시작 |
| 여러 서버 작업이 같은 쌍을 요청 | Redis 잠금을 공유해 중복 평가 억제 |
| 조회자 또는 후보 프로필 수정 | 이전 작업이 진행 중이어도 새로운 버전의 평가 시작 |
| 취소·잠금 소유권 변경·Redis 장애 | 취소된 잠금 해제, 다른 소유자의 잠금 보존, 로컬 중복 방지 |
| 모델 오류와 연속 조회 | `failed`를 표시하고 15초 동안 재호출 억제 |
| 새 BLE 관측 없음 | 기존 관측 권한으로 완료 결과 조회, 관측 시각 그대로 유지 |
| 일부 배치만 완료 | 완료된 결과부터 목록과 열린 상세에 반영 |
| 미관측·만료·발견 OFF | 새 조회로 정보 접근이나 대화 권한을 얻지 못함 |
| 오래 걸린 HTTP 응답·화면 종료·새 목록 | 낡은 응답이 최신 화면을 덮어쓰지 않음 |
| 네트워크 오류·숨긴 화면 | 재조회 간격 확대, 숨긴 화면에서는 빠른 HTTP 요청 없음 |
| 왜곡된 JSON·가짜 근거 | 기존 실패·원문 검증 규칙 유지 |

전체 서버 테스트 **323개**, 웹 테스트 **55개** 통과. 웹 lint와 production build 통과.
최신 `main`(`f7252fd`) 통합 후에는 서버 **338개**, 웹 **55개** 테스트와 웹 lint·build가
통과했다. 통합 검증에서는 모델을 추가 호출하지 않았다. 서버 통합 테스트는 임시 로컬 Redis를 사용했다. 테스트에 고정돼 있던 두 Redis 주소도
공통 테스트 설정을 따르도록 수정했다. 실제 모델·FCM 호출은 없다.

재현:

```sh
uv run python evals/bench/compact_replay.py --output evals/reports/compact-replay-2026-09-20.json

```

재생 스크립트에는 로컬에 저장된 `live-targeted-prompt2.json`, `live-targeted-fresh.json`이
필요하다. 이 파일들은 버전 관리 대상이 아닌 기존 평가 산출물이다.

## 선택과 남은 한계

스코어링과 이유 생성을 두 번 호출하도록 분리하면 대기 구간과 호출 수가 늘어난다.
상위 후보만 이유를 만드는 방식은 모든 후보의 이유를 제공하는 현재 동작도 바꾼다.
이번에는 한 번의 평가에서 필요한 내용을 유지하면서 반복 출력부터 줄였다.

배치를 무조건 1~2명으로 줄이거나 동시 요청 수를 크게 늘리는 방식은 여러 사용자에서
게이트웨이 요청 수와 입력 토큰, 대기열을 늘릴 수 있다. 배치 5·동시성 4는 유지한다.
`max_output_tokens`도 4096을 유지한다. 이전 1400 토큰 설정에서는 JSON 잘림으로 배치
전체를 잃은 기록이 있어 출력량 감소를 강제 중단으로 구현하지 않았다.

약 1초는 정상 네트워크·보이는 화면에서 결과를 **재조회하는 간격**이다. 실제 전달 시간의
상한이 아니다. 최초 BLE 보고 주기는 여전히 15초이며 백그라운드 화면은 빠르게 조회하지
않는다. 모델이 느리거나 여러 사용자가 동시성 4개를 공유하면 대기는 여전히 발생한다.
서버와 웹 번들을 함께 반영해야 새 조회 경로가 작동한다.

기존 실호출 예산 장부가 cap 240에 예약 포함 241이어서 새 모델 호출은 0건이다.
새 프롬프트의 실모델 지연·토큰 수·판단 품질·한계 누락 여부는 아직 검증하지 않았다.
기존 약 9초가 몇 초로 줄었다고 주장할 근거는 없다. 다음 실모델 검증에서는 후보 1·5·20·50명,
의도 충돌·모호한 소개·긴 소개와 동시 사용자를 포함해 출력 토큰·전체 지연·실패율·추천
품질을 같은 입력으로 비교해야 한다.
