# Redis 저장과 복원 계약

2026-09-20. [개발 기준](../../docs/development-contract.md), [API](../../docs/api-contract.md)를 따른다. 이전 방별 키·운영자 종료·1시간 삭제 규칙은 [이력](../../docs/history/event-mvp/server/docs/redis.md)으로 옮겼다.

## 기존 실행 기반

`server/`에서 `docker compose up -d --wait redis`로 실행한다. `/ready`는 Redis 연결 상태, `/health`는 API 생존 상태다. `REDIS_URL`과 Compose의 Redis 주소는 환경 설정을 따른다. 현재 클라이언트·준비 상태 기반과 제품 저장 구현을 구분한다.

Compose는 AOF `appendfsync always`와 영속 volume을 사용한다. `docker compose down`은 일반 종료이며 `down -v`는 제품 데이터 삭제를 동반하므로 일반 재시작 절차로 사용하지 않는다. 기존 설정의 실제 장애 복원은 V12에서 검증한다.

## 저장 객체

설치 사용자·인증 자격 연결, 프로필/입력 버전, 발견 참여, 임시 식별자 매핑, 근접 관측, 추천 결과, 두 사용자 쌍의 대화, 순번 메시지, 중복 방지 결과를 분리한다. 키 이름은 구현 때 API 필드와 함께 고정하며 room/event/request-acceptance 키는 만들지 않는다.

첫 메시지의 자격 검사·사용자 쌍 대화 생성·메시지 저장·순번·중복 방지는 경합에 안전하게 처리한다. 기존 대화의 추가 메시지는 당사자 권한을 검사하며 현재 근접성·발견 ON을 필수로 요구하지 않는다. Redis 스크립트 실행을 임의 실패의 자동 롤백으로 오해하지 않고 쓰기 전에 타입·입력을 확인한다. 외부 LLM은 저장 원자 작업 밖에서 실행한다.

## 수명

- 사용자·프로필·대화·메시지에 5분 TTL·행사 종료·시연 종료 삭제를 적용하지 않는다.
- 시연 데이터와 일반 데이터의 저장 경로·보관 조건은 동일하다.
- 임시 식별자·관측·추천 캐시·인증 수단 등 기술 데이터는 각각의 유효성을 관리한다. 그 만료가 메시지 삭제를 유발하지 않는다.
- 장기 보관/사용자 삭제 정책은 후속 운영 설계이며 현재 문서가 영구 보관을 보장하지 않는다.

## 검증

저장 성공 응답 뒤 서버/Redis 재시작을 수행해 이력·순번·중복 방지가 복원되는지 확인한다. 실행 시 기존 사용자 데이터를 무단 삭제하지 않는다. AOF·단일 디스크를 복제·백업·디스크 장애 복구와 동일시하지 않는다. 소켓·이벤트 알림 유실은 서버 이력 조회로 복구한다.
