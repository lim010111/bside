# AI 개발 계획 및 작업 경계

2026-09-20. Codex가 계획·오케스트레이션을 담당한다. 초기 구현·검증은 herdr의 별도 Claude 탭에서 완료했고, 후속 사용자 요청으로 개발·평가 작업자를 **Codex Astra low**로 이전했다. API·프론트는 다른 팀원이 개발 중이므로 이 계획은 AI 모듈의 내부 경계와 인계에 집중한다.

## 기준과 완료 조건

현재 `spec/prompts.md`, `docs/api-contract.md`의 AI 모듈 경계, `docs/planning.md`의 AI-D1~D6, `docs/validation.md`의 E01~E08을 기준으로 한다.

1. 서버가 전달한 조회자·후보의 소개, 의도, ID, 입력 버전을 받아 방향별 추천을 생성한다. 모든 유효 후보를 보존하고 성공·정보 부족·실패·미평가를 구분한다.
2. HTTPX 기반 비동기 게이트웨이 호출과 Pydantic 검증을 제공한다. 참가자 입력은 데이터로 처리하고 후보 창작·근거 없는 원문 인용·오래된 결과 노출을 막는 검사를 둔다.
3. 양쪽 입력 버전·조회 방향·모델·프롬프트·설정에 따른 캐시와 조절 가능한 알림 적합성 정책을 제공한다. 발견·관측·채팅 권한 및 실제 알림 발송은 서버 책임이다.
4. API 담당자가 호출할 인터페이스, 예시, 설정, 입력 변경 시 폐기 및 종료 시 자원 정리를 문서화한다. HTTP 엔드포인트와 프론트 파일은 이 작업에서 수정하지 않는다.
5. Claude가 오프라인 회귀 테스트와 Promptfoo 평가를 구성·실행한다. 실모델 비교와 후보 20명 성능 측정은 인증이 준비되면 수행하고 사용량·측정 조건·한계를 기록한다.
6. 기준선 대비 우위와 사람의 기대 결과는 실제 확인한 범위만 주장한다. Claude가 만든 기대값은 사람 검토 전 가설로 표시하고, 실제 모델 미호출 결과를 AI 품질 증거로 표시하지 않는다.

## 초기 작업 분담

- 구현 Claude: `server/app/ai/`, 필요한 서버 의존성 변경, `server/docs/ai.md`, 구현에 필요한 단위 테스트.
- 검증 Claude: `server/evals/`, `server/tests/test_ai_acceptance.py`, `server/docs/ai-validation.md`. 먼저 평가 사례·기준선·검증 계획을 만들고 구현 인터페이스 확정 후 연결한다.
- 독립 리뷰 Claude: `server/tests/test_ai_review.py`, `server/docs/ai-review.md`. 구현을 직접 수정하지 않고 결함을 재현·보고하며 수정 뒤 회귀를 확인한다. 실제 모델 호출은 검증 Claude 한 곳에서 수행한다.
- Codex: 작업 순서·경계·명세 대응 확인, Claude 피드백과 수정 지시, 사용자 결정 반영. 애플리케이션 코드와 테스트 코드는 직접 작성하지 않는다.

공유 작업 디렉터리의 기존 변경을 보존한다. 다른 팀원의 API·프론트·설정 변경을 되돌리거나 일괄 정리하지 않으며 커밋·배포는 이 계획의 완료 조건이 아니다.

후속 작업에서는 같은 소유 경계를 Codex Astra low 작업자에게 이전한다. 실제 추가 모델 호출·평가 도구 수정은 `ai-eval-astra-low`, 독립 검토는 `ai-review-astra-low` 탭이 맡는다. 상위 Codex는 상세 작업 지시와 보고서 검토, 커밋·푸시를 담당한다.

## 진행 순서

1. 독립 AI 입출력 모델·호출 인터페이스를 구현하고 인계 예시를 고정한다.
2. 게이트웨이·프롬프트 주입·결과 검증·캐시·알림 정책을 구현한다.
3. E01~E08, 부분 실패, 모델의 잘못된 후보/버전, 캐시·임계값 변경을 검증한다.
4. Promptfoo로 같은 사례의 기준선·복수 모델을 비교하고 20명 성능을 측정한다.
5. 실패·리뷰 발견 사항을 수정하고 필요한 검증을 다시 실행한다.

## 외부 입력 및 미검증 사항

- 사용자가 `server/.env`에 `AI_API_KEY`를 설정했고 값 노출 없이 존재를 확인했다. 별도 URL은 없어 명세의 `https://ai.cs.kookmin.ac.kr/v1`을 실제 연결 확인 대상으로 사용한다. 검증 Claude가 모델 조회·최소 호출·복수 모델 평가를 담당한다. 비밀값은 출력·커밋하지 않는다.
- 사용자가 이번 구현에 교체 가능한 기본 프롬프트를 포함하고 추후 직접 관리하기로 확인했다. 외부 관리 서비스의 채택을 뜻하지 않는다.
- 사용자가 핵심 기대 순위를 확인했다. 같은 React 경험자의 배포 도움 의도에는 민서를, 장기 사이드프로젝트 동료 의도에는 영진·도윤을 우선한다. 영진·도윤 사이의 정확한 순서나 다른 평가 사례 전체를 승인한 것은 아니다.
- 인증된 모델 목록 조회는 HTTP 200으로 성공했다. 모델 목록에 있다는 사실과 실제 생성 호출 성공·추천 품질·성능은 별도로 검증한다.
- 주변 목록 즉시 표시·20명 추천 5초 이내는 검증 목표다. 독립 모듈 테스트 통과를 실제 API·Android 통합이나 성능 목표 달성으로 확대하지 않는다.

## 완료 기록

herdr의 `ai-implementation`, `ai-validation`, `ai-review` 탭에서 Claude가 코드·평가 도구·테스트를 작성하고 실행했다. Codex는 계획과 작업 경계, 사용자 결정 반영, 결함 수정 순서와 인계를 담당했다.

- 독립 AI 모듈: `server/app/ai/`. 방향별 의도 추천, 근거 검증, 상태 구분, 후보 보존, 비동기 배치 호출, Redis 캐시 어댑터, 현재 알림 정책 적용, 오래된 입력 결과 검사, 호출·토큰 사용량을 제공한다.
- [호출 및 설정 안내](../server/docs/ai.md), [실모델 평가 기록](../server/docs/ai-validation.md), [독립 리뷰](../server/docs/ai-review.md), [평가 재현 방법](../server/evals/README.md)을 작성했다.
- Claude의 최종 서버 테스트는 **231개 통과**했다. 독립 리뷰에서 재현한 구현·평가 도구 지적 **17건을 모두 수정·재검증**했으며 미해결 항목이나 `xfail`로 가린 결함은 없다.
- 두 실모델을 규칙·문자열 기반 기준선과 비교했다. 사용자 확인 E01/E02 우선순위, 조정용 사례, 기존 보류 사례, 프롬프트 고정 뒤 새로 작성한 보류 사례를 구분한다. 결과와 한계는 평가 기록에 남겼다.
- 선택 모델은 `claude-haiku-4-5`, 기본 프롬프트는 `2026-09-20.2` / `32db67109c375cf1`이다. 로컬 `server/.env`에는 기존 키를 보존하면서 게이트웨이 주소와 모델 설정을 추가했다. 비밀값은 저장소에 추가하지 않았다.
- 권장 설정은 배치 5·동시 호출 4·출력 상한 4096이다. 최종 프롬프트에서 후보 20명 첫 평가 3회 모두 20명 평가 성공, 중앙값 **8.878초**였다. 배치 2·동시 호출 10의 단일 실험은 **5.649초**였다. **초기 5초 목표는 미달**이다.
- 인메모리 캐시 재사용 중앙값 약 0.8ms는 동일 프로세스 실험값이며 Redis·HTTP·Android 전체 지연이 아니다. 실제 게이트웨이 금액은 단가 조회 권한이 없어 미확인이다. 후반 실행은 제공자가 보고한 토큰과 집계 완전성 여부를 기록한다.

API 라우터 연결, 현재 발견 참여·관측 재검사와 알림 중복 억제, 실제 Android 목록·알림·채팅 통합은 다른 담당자의 작업 경계다. 이 완료 기록은 AI 모듈과 평가 도구의 구현·검증에 해당하며 전체 제품 통합 완료를 뜻하지 않는다. 기존 사용자 변경을 보존했고 커밋·원격 게시·배포는 수행하지 않았다.

## 후속 요청 — 커밋·푸시와 추가 모델 평가

사용자가 위 완료 기록 이후 기존 작업의 구조적 커밋·푸시를 요청했다. AI 모듈·단위 테스트, 평가 도구·수용/리뷰 테스트, 결과·인계 문서로 변경을 나누어 현재 브랜치에 커밋하고 푸시한다. 기존 사용자 스킬 변경과 로컬 비밀값·평가 원본은 포함하지 않는다.

푸시 이후 Claude 평가 탭에서 게이트웨이의 Grok 4.6·Sonnet 5 모델 ID와 접근 가능 여부를 확인한다. 동결 프롬프트와 기존 기대값을 유지해 사용자 확인 사례를 포함한 동일 품질 검사 및 후보 20명 성능을 비교한다. 결과에는 모델별 성공·실패, 적용 검사 분모, 지연, 제공자 보고 토큰과 측정 한계를 기록한다. 추가 모델의 별칭이나 가용성이 불분명하면 다른 모델로 임의 대체하지 않는다.

기존 변경은 `7f8c26e`(구현), `b92656e`(평가 도구·테스트), `68f3409`(연동·검증·인계 문서)로 나누어 `origin/feat/ble-ai-recommendation`에 푸시했다. 추가 평가 전에 이번 작업의 Claude 구현·평가·리뷰 세션을 모두 compact한다.

추가 평가 계획은 다음과 같다. 이는 결과를 보기 전에 고정한 실행 범위다.

- Grok 4.6과 Sonnet 5에 기존 18개 사례를 적용한다. E08의 실패 주입은 실제 모델 품질에서 분리한다. 출력에 맞춰 프롬프트·기대값·정책을 바꾸지 않는다.
- 프롬프트 `2026-09-20.2` / `32db67109c375cf1`, 배치 5, 동시 4, 출력 상한 4096, 기존 제한 시간을 유지한다. 기본 모델 설정은 변경하지 않는다.
- 기존 Haiku·DeepSeek와의 직접 비교는 같은 프롬프트에서 이미 실행한 공통 7사례(E01/E02/E03/E05/N01/N02/N03)를 기준으로 한다. 이전 프롬프트의 전체 결과와 분모를 섞지 않는다.
- 후보 20명 콜드/캐시 성능은 모델마다 3회 측정한다. 실패 후보 재시도가 섞인 캐시 구간, 부분 토큰 집계, 기본 제한 시간 초과를 별도로 표시한다.
- 추가 생성 호출은 기존 누적 117회부터 총 240회 이내에서 관리한다. 이는 실행 범위를 제한하기 위한 오케스트레이터 상한이며 금액 예산이나 사용자 지정 상한이 아니다. 반복적인 동일 오류는 진단하고 무의미한 재호출을 줄인다.
- Claude 평가 담당이 실행·보고하고, 독립 리뷰 담당이 저장된 결과와 집계를 재확인한다. 실제 모델 호출은 평가 담당 한 곳에서 수행한다.

### 추가 평가 착수 상태

Claude 세 세션에서 `Compacted` 완료를 확인하고 평가·리뷰 지시를 전달했다. 그러나 2026-09-20 03:31 KST에 두 세션 모두 `You've hit your session limit · resets 7:40am (Asia/Seoul)`을 반환했다. 한도는 평가 대상 게이트웨이의 오류가 아니라 Claude 작업 세션의 사용 한도였다.

사용자는 이후 **Codex로 이전하되 개발 모델은 Astra low로 지정하고 상세히 지시**하도록 요청했다. 상위 Codex의 계획·오케스트레이션 역할은 유지하고, 코드·평가 실행·독립 검토는 herdr의 새 Codex 작업자 탭에서 `gpt-6-astra`, `model_reasoning_effort="low"`로 수행한다. 기존 Claude 자동 재개는 중복 호출 방지를 위해 취소한다. 위의 동결 프롬프트·평가 범위·운영 호출 상한은 유지한다.

### 세션 복구 후 진행

사용자가 직전 상위 세션을 열 수 없어 새 세션에서 재개를 요청했다. 대화 원본과 작업 트리를 확인해 기존 herdr의 Astra low 평가·리뷰 작업자를 그대로 재개했다. 복구 시 누적 129회의 장부와 저장된 기본 4건·진단 2건을 대조했고, 이 응답들을 재사용했다. 기존 구현·평가·문서·후속 계획 4개 커밋은 원격 `feat/ble-ai-recommendation`의 `3eec87e`까지 반영된 상태다.

두 신규 모델의 기본 18사례씩과 별도 진단 1건씩을 저장했다. 공통 7사례의 적용 검사 통과수는 Grok 4.6 **43/60**, Sonnet 5 **46/60**이다. 실제 17사례의 후보 77명에서 Grok은 평가 1명·근거 부족 8명·실패 68명, Sonnet은 평가 19명·근거 부족 16명·실패 42명이었다. 계약 검사 통과수를 추천 성공률로 해석하지 않는다. 기본 모델·프롬프트·기대값은 유지했다.

추가 실행 도구는 저장 응답 재사용, 중단 표식에 따른 자동 재호출 차단, 누락 응답의 분모 유지, 프롬프트·추론 설정 일치 검사, 입력 순서 기록의 출처 구분을 제공한다. 독립 리뷰가 집계 도구의 추가 4건 수정을 확인했다. 최종 성능·호출 장부·검증 기록은 [추가 모델 비교](../server/docs/ai-model-comparison.md)와 [인계 문서](ai-handoff.md)를 따른다.

후보 20명 cold/warm 3쌍씩도 완료했다. cold 중앙값은 Grok 20.059초, Sonnet 20.049초이나 대부분 후보가 timeout이며 5초 목표 미달이다. warm에도 재호출이 있어 순수 캐시 실측으로 주장하지 않는다. 추가 생성 91회(품질·진단 44 + 벤치마크 47), 누적 208/240회로 종료했다. 오프라인 평가 도구·gateway 정리 검증은 통과했다. 이후 사용자가 **Haiku 유지와 PR 생성**을 확정했다. 추가 평가·복구 산출물을 커밋하고 최신 `main`의 API·Android 작업을 통합·검증한 뒤 PR을 생성한다.

`main`의 `a85292f`를 통합하면서 API 계약·서버 README 충돌을 해결했다. API v0.1·OpenAPI·웹·Android 제품 코드를 보존하고 AI 모듈과 후속 어댑터의 경계를 명시했다. Redis 초기화 fixture를 API 테스트에 한정해 AI 오프라인 테스트가 무관하게 skip되지 않도록 했다. 별도 임시 Redis 7.0.15에서 전체 서버 **261개 통과·skip 0개**, Redis 없이 AI **227개 통과·skip 0개**를 확인했다. 모델 호출을 추가하지 않았고 기존 사용자 스킬 변경도 포함하지 않는다.
