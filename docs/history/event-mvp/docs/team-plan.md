AI 개발 도구는 각 담당자의 구현을 돕는 수단이다. 역할을 나눌 때는 **무엇을 만들고, 어디까지 바꾸고, 누가 동작을 확인할지**를 함께 정한다. 제품 범위는 [MVP 개발 기준](../../../development-contract.md), 필드·오류·갱신 방식은 [API 계약](api-contract.md), 실행 증거는 [검증 계획](validation.md)을 따른다.

서버 담당은 최종 통합 책임을 갖되 다른 담당의 코드까지 혼자 수정하지 않는다. 연결 문제가 생기면 데이터를 보내는 쪽과 받는 쪽 담당이 함께 확인하고 각자 소유한 코드를 고친다. 검증·시연 담당에게 배포 장애나 전체 코드 병합 해결을 단독으로 맡기지 않는다.

Q15 이후 위임에 따른 웹·서버 스택과 첫 통합 작업은 [MVP 개발 기준](../../../development-contract.md)을 따른다. 서버 담당은 메시지 저장·재접속 이력과 행사 종료 검사를 책임지고, 프론트 담당은 같은 계약에 맞춰 화면을 복원한다. 이 기술 선택이 미정인 세 사람의 실명 배정을 대신하지는 않는다.

Q9에서 **추천 점수 산정 방식은 AI 담당에게 위임**했다. LLM-as-judge는 후보일 뿐 확정 스택이 아니다. AI 담당은 같은 사례에 대한 순위 품질·근거·응답 시간·호출 비용을 비교하고, 프론트·서버와는 결과 형식 및 미평가·실패·갱신 계약을 먼저 맞춘다. 방식 선택이 참가자 목록의 임의 삭제로 이어져서는 안 된다. 사용자 의도 불일치는 우선순위를 낮추는 요인으로 유지한다.

Q17에서 Q10의 임시 공개 범위를 변경했다. **목록의 사용자 배너를 누른 상세 화면에서 자기소개·교류 의도·추천 이유를 보여준다.** 숫자 점수 표시는 보류한다. 프론트·서버 담당은 목록 배너와 상세 응답을 구분하고, AI 담당은 조회자와 후보에 맞는 추천 이유를 제공한다. 입력 화면의 공개 안내도 두 원문을 상세에서 볼 수 있다는 기준으로 맞춘다.

Q11에서 **별도 수락 절차 없는 1:1 채팅**이 핵심 범위에 포함됐다. 프론트와 서버 담당은 메시지 전송·수신·대화 이력 계약을 함께 맞추고, 검증 담당은 두 실제 사용자 간 송수신을 확인한다. 별도 대면 확인 기능은 현재 필수 작업으로 배정하지 않는다.

Q12에 따라 사진 첨부는 현재 MVP 작업에서 제외하는 방향이며, 파일·읽음·푸시 등 부가 채팅 기능은 일단 고려하지 않는다. 이를 팀 작업이나 개발 착수의 선결 조건으로 추가하지 않는다. 텍스트 송수신·복원에 필요한 구현 계약은 확정된 사용자 행동에 맞춰 작성한다.

Q13~Q15에 따라 검증 담당은 실제 송수신 후 새로고침과 브라우저 재실행을 각각 수행해 입력·대화가 유지되고 중복 참가자가 생기지 않는지 확인한다. 한쪽이 앱을 닫은 상태에서도 다른 쪽 목록에 남고, 그동안 보낸 메시지가 복귀 시 나타나야 한다. 행사 종료 후에는 목록·대화 열람과 전송이 끝나야 한다. 프론트의 종료 화면과 서버의 접근 종료를 함께 확인한다. 실제 정리 시점과 대상은 API 계약의 개발 기본값을 따른다.

Q18에 따라 자기소개·교류 의도 수정과 참여 중단을 구현 경계에 추가한다. 프론트·서버는 중단한 참가자의 목록 제외·새 송수신 거부·기존 이력 열람을 함께 확인하고, AI 담당은 입력 수정 후 오래된 순위·이유가 현재 결과로 표시되지 않게 한다. Q20에 따라 같은 참가자로 재개하고 기존 대화를 유지한다. 중단 중 거부된 새 전송은 재개 후 자동 전달하지 않는다.

Q19에 따라 검증·시연 담당의 우선 산출물은 **교류 의도만 다른 사례의 실제 추천 비교, 두 사용자의 실제 답장, 참가자·행사 운영진의 수요 관찰**이다. 운영진 대시보드는 개발 작업으로 배정하지 않는다. 문제 해결력·AI·완성도·사업화·발표의 증거를 [평가 계획](topic-evaluation.md)에 연결한다.

## 개발이 익숙하지 않은 분에게 제안할 구체 작업

단순히 ‘테스트를 해주세요’라고 맡기지 않고 실행 절차·기대 결과·검토자를 붙인다. 다음 작업에서 우선순위를 정하며, 전부 동시에 맡기는 목록은 아니다.

| 작업 | 처음 제공할 것 | 산출물 | 검토자 |
| --- | --- | --- | --- |
| **교류 의도 평가 사례** | 합의된 본인 정보·교류 의도 입력 형식과 예시 1개 | 비슷한 사람 찾기, 조언받기, 취미 대화, 정보 부족 등 8~12개 제안 사례와 기대 결과 | AI 담당. 기대 결과는 모델 출력에 맞춰 사후 변경하지 않고 사람이 근거를 확인 |
| **두 사용자 흐름 확인** | 앱 접속 방법과 두 역할의 행동 순서 | 각 단계 성공·실패, 입력, 화면·로그 증거와 재현 순서 | 관련 프론트·서버 담당 |
| **시연 데이터 준비 코드** | 고정된 API 또는 fixture 형식과 실행 예시 | AI 도구로 작성한 데이터 생성·주입 보조 스크립트 | 서버 담당. 개발·시연용 데이터임을 명시하고 실제 이용자 성과와 분리 |
| **평가 결과 정리 코드** | AI 담당이 제공한 실행 명령과 결과 형식 | 입력·추천·설명·기대 결과를 나란히 비교하는 로컬 리포트 | AI 담당. 초기에는 문서·표만으로 시작하고 반복 작업이 생길 때 구현 |
| **발표·영상 구성** | 공식 배점과 실제 구현 범위 | 5분 발표 구성, 시연 영상, 예상 질문과 답변 초안 | 전원. 기술·사업 근거는 해당 담당이 확인 |

그분이 코드 구현을 더 원하면 B안의 제한된 구성요소 작업도 가능하다. 예를 들어 빈 목록·오류 안내처럼 입력과 표시 결과가 명확한 구성요소 하나를 맡고, 김성빈이 인터페이스와 통합을 책임지는 방식이다.

## AI 개발 도구를 쓰는 공통 작업 방식

### 작업 지시를 같은 근거에서 시작한다

모든 담당자가 도구에 [MVP 개발 기준](../../../development-contract.md), [API 계약](api-contract.md), [공통 용어](../../../../CONTEXT.md), 담당 검증 ID를 명시적으로 제공한다. 결정의 배경이 필요할 때 [인터뷰 기록](planning.md)을 읽는다. 특정 파일이 모든 도구에서 자동으로 읽힌다고 가정하지 않는다. [main 비교와 채택 결과](../../../reviews/baea751.md)를 함께 참고한다. `spec/*`의 지침은 현재 계약으로 갱신했지만, 기존 mock 코드에는 교체할 동작이 남아 있다.

작업 요청은 다음 형식으로 작성할 수 있다.

```text
목표: 사용자의 어떤 행동을 동작시키는가
근거: 현재 제품 결정과 이 작업의 계약·예시
수정 범위: 담당 파일 또는 디렉터리
입력·출력: 다른 담당과 공유한 예시
완료 조건: 직접 실행해서 확인할 행동과 실패 상황
인계: 변경 요약, 실행 방법, 확인 결과, 남은 문제
```

예를 들어 AI 담당에게는 의도 해석과 후보 결과 생성을 맡기고, 프론트 화면·서버 세션 API까지 함께 재작성하게 하지 않는다. 공유 계약을 바꿔야 하면 그 변경을 먼저 관련 담당에게 전달하고 예시도 같이 갱신한다.

### 작업공간과 파일 소유를 나눈다

팀원별 작업 브랜치와 별도 작업공간을 사용한다. 한 사람이 여러 AI 세션을 동시에 실행할 때도 각각 별도 디렉터리·브랜치를 사용하는 안을 추천한다. Git은 `worktree`로 같은 저장소의 여러 브랜치를 별도 디렉터리에 동시에 둘 수 있다. [Git 공식 문서](https://git-scm.com/docs/git-worktree)

아래는 병합한 `web/`·`server/`에 맞춘 소유 경계다. 프론트·서버 실행 설정과 잠금 파일은 이미 있으므로 T00은 새 scaffold 생성이 아니라 계약 예시·실행·연결 경계를 맞추는 작업이다.

| 경계 예시 | 변경 책임 |
| --- | --- |
| `web/` | 김성빈. B안이면 보조 담당에게 특정 구성요소만 지정 |
| `server/app/`의 공통 설정·라우터·저장과 `server/compose.yaml` | 서버·통합 담당. AI 모듈은 아래 경계로 분리 |
| `server/app/ai/` (구현 때 생성) | AI 담당 |
| `fixtures/`, `docs/validation.md`, 발표·영상 산출물 | 검증·시연 담당. 형식 변경은 소비하는 담당과 조율 |
| 공통 계약·루트 실행 설정·의존성 파일 | 주 담당 1명을 지정하고 관련 변경을 함께 검토 |

### 통합 전 확인을 사람이 소유한다

각 담당자가 생성된 코드의 diff와 직접 실행한 결과를 확인한다. 작성에 쓴 도구의 ‘완료’ 메시지만으로 완료 처리하지 않는다. 계약·공개 범위·AI 의미가 바뀌는 수정은 연결되는 다른 담당이 검토한다. 개발이 익숙하지 않은 분의 코드는 담당 경계의 구현자가 검토한다.

GitHub에서는 PR의 `Files changed`에서 변경 diff를 읽고 줄별 의견과 전체 리뷰를 남길 수 있다. 이 기능을 사용하되 현재 저장소에서 리뷰가 강제된다고 가정하지 않는다. [GitHub 공식 문서](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request)

## 역할별 개발 작업과 통합 순서

아래는 A안을 기준으로 나눌 수 있는 작업이다. 김성빈 외 세 역할의 실명은 팀이 정한다. 각 행의 주 담당이 결과를 소유하되 상대 경계의 코드는 해당 담당이 수정한다. T00 뒤에는 T01·T02·T03·T04를 병렬로 시작할 수 있다.

| 작업 | 주 담당 | 선행 | 범위 | 완료 증거 |
| --- | --- | --- | --- | --- |
| T00 실행·계약 기반 | 서버·통합, 전원 확인 | 현재 개발 기준 | 기존 `web/`·`server/` 실행 재현, mock 필드를 API 계약으로 갱신, 같은 출처 개발 프록시·배포 경계, Redis 저장 계약, 공통 예시. 실제 비밀값은 제외 | 새 작업공간에서 같은 명령 실행, 프론트·서버가 같은 예시를 읽음 |
| T01 화면 흐름 | 김성빈 | T00 | 입장·목록 배너·상세·내 정보·채팅·중단/재개·종료 화면. 처음에는 같은 예시 데이터 사용 | V01·V02 화면 흐름, 실제 API 연결 위치와 오류 상태 명확 |
| T02 행사·참가자 API | 서버·통합 | T00 | 브라우저 세션, 방 준비·QR 참여 링크, 입력·조회·수정·중단·재개, 영속 DB | V01·V02·V07의 API 동작과 동일인 복원 |
| T03 실제 추천·평가 | AI | T00 | 공통 입력·출력 모듈, 모델 선택·검증·실패, 기준선·시간·비용 비교 | E01~E08 결과와 V09·V10, 실제 모델 호출 근거 |

| T05 첫 실제 통합 | 서버·통합, 김성빈·AI 협업 | T01·T02, T03의 예시 응답 계약 | 두 브라우저 입장·목록·상세를 실제 서버로 연결. 추천은 예시/실제를 표시 | 실제 입력이 서로 보임. 가짜 참가자 수·고정 추천을 실측으로 사용하지 않음 |
| T06 채팅·복원 | 서버·통합, 김성빈 협업 | T05 | 저장·중복 방지·이력·SSE와 프론트 합치기, 부재·재시작 복원 | V04~V08, 실제 두 사용자 답장 |
| T07 추천·상태·종료 통합 | 서버·통합, 김성빈·AI 협업 | T03·T06 | 실제 순위·상세 이유, 수정·중단/재개 버전, 수동 행사 종료·정리 | V03·V07·V09~V12 |
| T08 검증·영상·발표 | 검증·시연, 전원 확인 | T07, 관찰은 T04부터 진행 | V01~V12 재현 기록, AI 비교·수요 근거, 5분 리허설과 백업 영상, PPT/PDF | 실제 구현과 발표 일치, 남은 실패·미검증 사항 표시 |

처음부터 예시 추천 응답으로 인터페이스를 연결하고 이어 실제 AI로 교체한다. T03 전체 완료를 기다리느라 목록·채팅의 첫 통합을 미루지 않는다. 반대로 예시 응답 성공을 AI 통과로 기록하지 않는다.

## 각자의 AI 도구에 전달할 시작 지시

아래 공통 문장 뒤에 자신의 작업 행과 소유 경계를 붙인다. 이 문장은 도구 실행이나 PR 생성이 이미 이루어졌다는 뜻이 아니다.

```text
이 저장소의 docs/development-contract.md, docs/api-contract.md,
CONTEXT.md와 docs/validation.md를 먼저 읽는다.
과거 spec/*와 프로토타입은 참고 자료이며 현재 계약과 충돌하면 현재 계약을 따른다.
내 작업은 Txx이며 수정 범위는 [담당 디렉터리]다.
다른 역할의 파일을 임의로 바꾸지 말고 공통 계약 변경은 먼저 문서와 예시에 제안한다.
완료 조건은 [Vxx / Exx]다. 실제 실행 결과, 남은 문제, 인계 방법을 기록한다.
가짜 응답과 실제 서버·모델 결과를 구분하고 없는 검증 결과를 만들어내지 않는다.
```

개발이 익숙하지 않은 분에게는 T04부터 배정하는 A안을 추천한다. 구현자가 실행 방법과 기대 결과를 제공하고, 해당 담당이 결과를 검토한다. 코드 작업을 원하면 가상 시연 입력 생성·평가 결과 표 작성처럼 경계가 작은 산출물을 붙인다. 서버 배포 장애나 전체 병합 해결을 단독 책임으로 주지 않는다.
