# Bside 기획 커밋 검토

검토일: 2026-09-19. 대상: [d18f5e1e65b663232b0a08edf7e33922228abc81](https://github.com/lim010111/kosscchthon/commit/d18f5e1e65b663232b0a08edf7e33922228abc81), Sungblab, `docs: Bside 기획 확정 및 문서 구조 정리`.

**판정: 행사 현장의 첫 대화로 좁힌 제품 방향은 채택할 가치가 있다. 다만 현재 커밋을 그대로 확정 개발 명세와 발표 근거로 쓰기는 어렵다.** 가장 먼저 고칠 것은 문서 간 범위 충돌, 대상 사용자와 매칭 규칙의 불일치, 실제 교류를 확인하는 흐름이다.

원격 커밋을 별도 사본으로 읽었다. 로컬 main에 병합하지 않았으며 기존 작업 파일은 보존했다. 변경은 26개 파일, 추가 3,410줄·삭제 14줄이다. 앱 소스·빌드 설정·실행 테스트는 없는 문서 커밋이므로 아래 내용은 구현에서 관찰한 장애가 아니라 명세의 결함과 근거 검토다. README, 명세 6종, 시드 데이터, 관련 조사·발표 근거를 중심으로 검토했다. 시장 조사에 등장하는 모든 수치의 전수 검증은 하지 않았다.

## 평가 기준에 따른 방향 판단

| 기준 | 살릴 방향 | 현재 감점 위험 |
| --- | --- | --- |
| 문제 해결력 30 | 행사에 혼자 온 참가자, 현재 상태, 첫마디라는 구체적 장면 | 실제 상대를 찾는 단계가 없고 차별성 근거 일부가 틀림 |
| AI 활용 15 | 찾는 것과 제공할 수 있는 것을 연결하고 이유를 설명 | 일반 행사 사용자를 기술 도움 매칭 규칙이 걸러냄. AI 필요성 주장·예시가 부정확함 |

| 사업화 15 | 참가자와 구매자 후보인 운영진을 구분 | 좋아요·가짜 집계를 실제 교류 성과로 읽히게 함. 가격·구매 의사가 검증되지 않음 |
| 발표·질의응답 15 | 5분에 맞춘 시연과 예상 질문 준비 | 시장 공백·AI 독점성·무저장 등을 입증된 사실처럼 단정 |

행사라는 범위는 초기 사용자를 같은 장소에 모으는 경로와 운영진의 도입 이유를 함께 검증하기 좋다. 단, QR을 보여주는 것만으로 참여율이나 구매 의사가 보장되지는 않는다. React 화면을 웹과 앱에서 공유하는 선택도 검토 가능한 방향이다. 스택의 가능성과 기기 간 검증 완료는 구분해야 한다.

## 수정이 필요한 사항

P1은 개발 계약이나 핵심 성과를 왜곡하므로 착수 전에 정리할 항목이다. P2는 해당 기능 구현·발표 전에 고칠 항목이다. 숫자는 예상 심사 점수와 무관하다.

### R1 · P1 · ‘확정 명세’ 안에 서로 다른 MVP가 있다

근거: [MASTER 162행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/MASTER.md#L162), [PRD 93행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/PRD.md#L93), [protocol 1행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/protocol.md#L1), [roadmap 28행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/roadmap.md#L28).

MASTER는 BLE 1:1 채팅을 P1으로 두고 서버 채팅 폴백까지 요구한다. PRD는 채팅을 범위 밖으로 두고 BLE는 근접 표시만 허용한다. protocol은 BLE 포기·PWA를 선언하고, roadmap은 제출본에서 BLE와 채팅을 모두 제외한다. MASTER의 스택 확정과 PRD의 스택 결정 대기도 충돌한다.

화면 담당이 채팅을 제외하고 BLE 담당이 자유 채팅을 구현하면 JSON 규격을 공유해도 통합되지 않는다. **현재 MVP의 기능·플랫폼·시연을 한 버전으로 맞추고, 구버전에는 대체 문서와 상태를 표시해야 한다.** 문서 지도만으로 우선순위 충돌이 해결되지는 않는다.

### R2 · P1 · 주인공은 일반 행사 참가자인데 AI는 기술 도움 요청만 처리한다

근거: [protocol의 MEETUP 상태 87행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/protocol.md#L87), [prompts의 분류 25행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/prompts.md#L25), [후보 필터 45행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/prompts.md#L45).

제품은 `FIRST_TIME`끼리 연결하고 `LOOKING_FOR`와 `CAN_SHARE`를 매칭한다고 설명한다. 그러나 추출기는 기술적 사실을 추출하고, 후보는 `STUCK × EXPERIENCED`만 통과시킨다. ‘처음 왔어요, 다른 참가자와 프로젝트 얘기하고 싶어요’인 두 사람은 SOCIAL 또는 UNCLEAR로 분류되어 핵심 매칭에서 제외된다. ‘첫 사용자 피드백 필요 ↔ 새 서비스 체험 희망’도 이 필터로는 보장되지 않는다.

**행사 첫 대화를 유지한다면 현재 교류 의도·제공 의사·대화 가능 상태를 다루는 규칙으로 맞춰야 한다.** 기술 도움 연결만 구현한다면 제품의 첫 대상과 발표도 그 장면으로 좁혀야 한다. 또한 prompts는 조력자가 건넬 첫마디를 출력하지만 scenario는 도움 요청자에게 문장을 보여준다. 카드 수신자와 첫마디 화자도 계약에 포함해야 한다.

### R3 · P1 · 대면 전환 단계 없이 ‘좋아요’를 실제 대화로 집계한다

근거: [protocol 집계 105행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/protocol.md#L105), [PRD 지표 178행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/PRD.md#L178), [scenario 현실 전환 111행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/scenario.md#L111).

좋아요는 추천에 대한 반응이다. 상대가 응답하지 않았거나 만나지 못해도 현재 정의상 ‘대화 시작’이 증가한다. 화면의 닉네임을 현실의 어느 사람과 연결할지도 필수 흐름에 없어서, 영상에서 등장인물이 서로를 이미 아는 상황으로 공백을 메우게 된다. BLE 발견 역시 사람을 시각적으로 식별하는 계약을 대신하지 않는다.

**추천 반응·제안 수락·대면 확인을 구분하고, 현장에서 상대를 찾는 방법을 넣어야 한다.** 예를 들어 만남 위치와 화면 식별 표시를 사용하고 실제 대화 후 확인을 받는다. 확인 방식의 한계를 발표에 명시한다. 대시보드의 하드코딩 예시는 ‘예시 데이터’로 표시하며 실제 사업 성과나 현장 실적으로 집계하지 않는다.

### R4 · P1 · 만료·데이터 경계가 제품 약속과 맞지 않는다

근거: [MASTER P2 168행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/MASTER.md#L168), [PRD 비기능 요구 163행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/PRD.md#L163), [protocol 서버 모델 42행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/protocol.md#L42), [prompts 입력 80행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/prompts.md#L80).

‘지금 대화 가능’, ‘5분 후 만료’, ‘행사 종료 후 소멸’을 약속하지만 상태 만료 실동작은 P2다. 구현을 생략하면 떠난 사람이 목록·추천에 계속 남는다. 메모리 dict는 프로세스가 살아 있는 동안 데이터를 보유하므로 DB가 없다는 사실만으로 이 약속이 성립하지 않는다.

또한 원본 프로필이 경계를 넘지 않는다고 쓰면서 서버 모델은 닉네임·소속·note를 보유하고 AI 입력에도 note를 넣는다. ‘경계’가 다른 참가자 화면인지, 우리 서버인지, 외부 AI인지 불명확하다. **상태 만료·방 종료를 핵심 동작에 포함하고, 참가자 공개 필드·서버 보유 필드·AI 전송 필드·삭제 대상을 나눠 명시해야 한다.** 외부 제공자의 보유 정책은 별도 확인 대상이다.

### R5 · P1 · 국내 경쟁 공백 주장이 공식 서비스와 충돌한다

근거: [MASTER 102행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/MASTER.md#L102).

‘이벤터스·온오프믹스·페스타 중 참가자 매칭을 하는 곳이 하나도 없다’고 단정한다. 그러나 이벤터스는 셀러·바이어 비즈니스 미팅과 성과 분석을 지원하는 [공식 비즈매칭 솔루션](https://event-us.kr/hostcenter/solutiontype/bizmatching)을 제공한다. 일반 참가자의 즉흥 첫 대화와는 범위가 다르지만, 국내 매칭 서비스 부재를 근거로 삼을 수는 없다.

**차별성은 현장의 짧은 입력·현재 상태·즉시 대면 전환이라는 검증 가능한 경험으로 좁혀야 한다.** ‘국내 최초·유일’과 경쟁 서비스 전면 부재 주장은 제거한다.

### R6 · P1 · 팀이 공유할 실행 계약과 현재 시드 데이터가 맞지 않는다

근거: [protocol API 175행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/protocol.md#L175), [data/profiles.json](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/data/profiles.json), [README의 시드 안내 69행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/README.md#L69).

입장 API는 `nick/status/note`를 요구하지만 시드 3개 모두 이 필드가 없고 이전 상세 프로필 구조를 사용한다. 변환 규칙이 없어 화면·서버·AI 담당이 서로 다른 예시를 쓰게 된다. SSE도 이벤트 이름·payload·수신 대상·재접속 시 목록 재전송이 없고, AI 출력과 사용자에게 전송하는 match 객체를 연결할 ID·버전 규칙이 없다.

**현재 시드, 입장 응답, 목록, 매칭 이벤트, 실패 응답 한 세트를 고정해야 한다.** AI 처리 중 사용자가 상태를 바꾸거나 퇴장했을 때 오래된 결과를 버리는 기준도 필요하다. 공개되는 회원 ID와 본인 변경 권한은 구분해야 한다. 명세대로 공개 ID만으로 상태·퇴장을 변경하게 만들면 다른 참가자의 상태를 조작할 수 있으므로, 계정 없이도 세션 소유권을 확인하는 계약을 넣는다. 실제 취약 코드가 존재한다는 판단은 아니다.

### R7 · P2 · AI 필요성 주장이 틀린 예시와 비교에 기대고 있다

근거: [MASTER 113행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/MASTER.md#L113), [scenario 대조 장면 130행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/scenario.md#L130).

‘배포·CI 경험자 찾음’과 ‘작년에 도커 CI 구축해봄’에는 `CI`가 겹친다. ‘겹치는 단어 0개’ 자막은 사실과 다르다. ‘상보성은 유사도의 반대이며 LLM만 판단 가능’도 입증되지 않았다. 임베딩은 질문과 답변처럼 다른 역할의 텍스트를 연결하는 비대칭 검색에도 사용된다. [Sentence Transformers 공식 설명](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)

**AI의 가치는 자유 입력의 해석·관계 판단·근거 있는 첫마디에서 비교해야 한다.** 의도 필터+태그 또는 임베딩 기준선과 동일한 사례로 비교한다. ‘둘 다 STUCK인 사람을 제외함’은 이미 코드 필터가 수행하므로 그 결과를 LLM 성능 증거로 쓰지 않는다. 임베딩이 이 제품에서 더 낫다는 평가도 아직 수행하지 않았다.

### R8 · P2 · 후보 필터만으로 ‘5회 이하 호출’이 보장되지 않는다

근거: [prompts 138행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/prompts.md#L138), [MASTER 121행](https://github.com/lim010111/kosscchthon/blob/d18f5e1e65b663232b0a08edf7e33922228abc81/spec/MASTER.md#L121).

같은 방에 STUCK 10명·EXPERIENCED 10명이 있고 아직 알림을 보내지 않았다면 적격 쌍은 100개다. EXPERIENCED 19명이 있는 방에 STUCK 1명이 새 note를 쓰면 그 저장 한 번에 후보가 19개다. ‘새 note 시에만 실행’이나 미알림 필터는 호출 상한이 아니다. 알림을 보내지 않은 불일치 결과도 캐시하지 않으면 계속 재판정한다.

**호출 단위를 사람·저장 이벤트·행사 중 하나로 명확히 하고, 상위 후보 K개·변경 버전별 결과 캐시·동시성·시간 제한을 정한다.** 강도 임계값은 모델이 자가 생성한 점수이므로 실측 정확도로 부르지 않는다. 검증기에는 `match=false/NONE` 거부, 입력 타입·유한 숫자, 현재 동의·상태·만료 재확인도 필요하다. API 장애와 적합한 후보가 없음은 별도 상태로 표현한다.

## 추가로 발표·기술 검증 전에 정리할 내용

- **설치 없음과 BLE 직접 대화:** 일반 웹 입장과 Android 앱 BLE 경로를 나눠 설명해야 한다. QR로 웹을 연 사용자가 곧바로 네이티브 BLE 채팅을 쓸 수 있는 것은 아니다. Capgo는 공식적으로 peripheral 광고를 제공하며, 현재 공개 [타입 정의](https://github.com/Cap-go/capacitor-bluetooth-low-energy/blob/main/src/definitions.ts)에는 GATT 서비스·수신·알림 API도 있다. 따라서 Capacitor 방향 자체를 불가능하다고 볼 근거는 없다. 사용할 버전을 고정하고 실제 2대에서 설치→권한→양방향 교환을 확인해야 한다. 협상된 MTU, 긴 한글, 연결 끊김을 다루는 계약도 아직 필요하다.
- **시장 통계 해석:** [Brella의 30% 문구](https://www.brella.io/blog/event-networking-metrics-to-track)는 플랫폼 참여자 중 미팅 예약 비율을 점검하라는 예시다. 시장 전체가 실패했다는 관측치가 아니다. [TechBBQ 사례](https://www.brella.io/success-story/techbbq)는 2021년 4,500명 이상 중 2,600명 이상 참여, 미팅 수락률 39%를 보고한다. 채택률·예약률·수락률은 분모가 다르며, 앱이 무거워서 이 수치가 나왔다는 인과관계도 이 자료만으로 증명되지 않는다.
- **법 적용 단정:** PRD 163행과 발표 대본의 ‘GPS를 안 쓰므로 위치정보법 신고 대상 아님’은 현재 데이터 흐름 검토나 적용 근거 없이 확정할 수 없는 문구다. 이번 검토에서는 해당 면제 주장을 확인하지 못했다. 확인된 수집 방식만 기술하고 이 결론을 발표 근거에서 제외할 것을 권한다. 이는 별도 승인 절차를 요구하거나 반대로 신고 의무가 있다고 판정하는 것이 아니다.
- **가격과 수요:** 행사당 30~50만원은 가격 가설로 표시한다. 다른 제품 요금이나 캡스톤 예산이 이 서비스의 지불 의사를 입증하지는 않는다. 운영진에게 현재 네트워킹 문제·도입 조건·다음 행사 재사용 의사를 확인할 필요가 있다.

## 권장 수정 순서

1. **한 문장의 제품과 한 버전의 MVP를 맞춘다.** 행사 첫 대화를 유지할지, 해커톤 도움 연결로 한정할지 정하고 MASTER·PRD·protocol·prompts·scenario·roadmap에 같은 범위를 반영한다.
2. **완료 지점을 대면 교류로 잡는다.** 현재 상태→발견→대화 계기→상대 식별→대면 확인을 실제 두 사용자로 검증한다. 웹 기본 흐름이 완성된 뒤 BLE의 추가 가치를 비교하는 안을 추천한다. BLE가 필수 제품 요구라면 초기에 별도 기술 검증으로 성립 여부부터 확인한다.
3. **시드와 통신 계약을 맞춘다.** 상태·유효기간·회원 변경 권한·매칭 결과·SSE 이벤트·실패 상태를 고정하고 동일한 fixture를 공유한다.
4. **AI·집계·발표 근거를 검증한다.** 기준선 비교, 호출 상한, 사실·가설·예시 데이터 구분을 반영한다. 자유 채팅과 운영진 대시보드 확대보다 이 작업을 우선한다.

검증 결과: 시드 JSON 파싱 성공, 현행 입장 필드 누락 3개 프로필 확인, AI 예시 공통 토큰 `CI` 확인, 적격 후보 100쌍·단일 저장 19쌍 반례 계산, 공식 경쟁 서비스·AI 검색 설명·BLE API 확인. 앱 빌드, 실기기 통신, 게이트웨이 호출, 사용자 인터뷰와 구매 의사 검증은 수행하지 않았다.
