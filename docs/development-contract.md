# MVP 개발 기준

상태: **Q1~Q20과 최신 main 비교를 반영한 개발 기준. 충돌 시 더 나은 방식을 채택하라는 사용자 위임에 따라 기술 선택을 갱신했다.** 제품 결정의 원본은 [planning.md](planning.md), 용어는 [CONTEXT.md](../CONTEXT.md)다. 이 문서는 현재 MVP 범위와 행동의 기준이고 [API 계약](api-contract.md)은 그 구현 인터페이스다. 현재 구현은 mock 화면과 서버 기반까지이며 이 문서 전체가 구현됐다는 뜻은 아니다. 입력 한도·세션·정리 주기 등은 사용자 발언이 아닌 개발 기본값으로 구분한다.

## 제품과 MVP 범위

> 행사·밋업 참가자가 지금 만나고 싶은 사람을 자유롭게 설명하면, 같은 행사 방에서 양쪽 의도에 맞는 상대를 찾아 1:1 채팅을 시작하도록 돕는다.

검증할 문제는 행사장에 사람이 있어도 누가 어떤 교류를 원하는지 알기 어려워 대화 상대를 고르는 부담이다. 실제로 이 부담이 줄어드는지는 참가자 관찰과 추천 비교로 확인한다.

| 이번에 완성할 것 | 보류·제외할 것 |
| --- | --- |
| QR·링크, 계정 없는 닉네임·두 자유 입력, 같은 브라우저 복원 | 계정 가입·기기 간 동기화·일상/데이팅 확장 |
| 같은 행사 참가자 목록, 양쪽 의도에 따른 추천, 배너에서 상세 확인 | BLE·정확한 거리·상시 플로팅 UI |
| 상세의 소개·찾는 사람·추천 이유, 두 원문 수정 | 숫자 점수 표시·첫마디 자동 생성 |
| 바로 시작하는 1:1 텍스트 대화, 부재 중 보관, 중단·재개 | 사진·파일·읽음·앱 종료 후 푸시의 세부 기능 논의 |
| 운영자의 방 사전 준비·수동 종료, 종료 후 열람·전송 중단 | 방 생성 관리 화면·운영진 대시보드·대면 확인 기능 |
| 의도별 추천 비교·실제 답장 시연 | 검증하지 않은 수요·개선율·대면 횟수 주장 |

사진 제외는 기술적 전송 불가능이 아닌 현재 범위 선택이다. 나머지 부가 채팅 기능은 Q12에 따라 보류하며 승인된 필수 기능으로 되살리지 않는다.

## 개발 기준으로 선택한 구성

| 경계 | 선택 | 이 프로젝트에서의 이유 |
| --- | --- | --- |
| 화면 | 모바일 웹, React + Vite + JavaScript/JSX | main에 추가된 화면·CSS·컴포넌트를 유지한다. TypeScript 전환을 선행 작업으로 넣지 않고 JSDoc·공통 예시와 서버 검증으로 데이터 경계를 맞춘다. |
| 서버 | FastAPI + uvicorn, Python | 행사 참여·저장·채팅 API를 담당하고 AI 담당의 추천 모듈을 연결한다. |
| 전달 | REST로 메시지 전송·이력 조회, SSE로 변경 알림 | 브라우저를 닫은 동안의 메시지는 저장소에 남기고 재접속 때 조회한다. SSE 연결 자체를 보관 수단으로 취급하지 않는다. |
| 저장 | Redis + AOF + 영속 volume, 단일 인스턴스 | main의 클라이언트·설정·Compose를 재사용한다. `appendfsync always`로 저장 응답의 내구성을 강화하고, 참가자·메시지에 5분 TTL을 적용하지 않는다. 저장 모델·중복 방지·원자적 갱신은 아직 구현할 부분이다. |
| 배포 경계 | 화면과 API를 같은 HTTPS 출처로 제공, 초기 애플리케이션 worker 1개 | 기존 OCI·Nginx 배포안을 활용한다. 정적 화면과 `/api`를 한 출처로 연결해 쿠키·SSE 경계를 단순하게 유지한다. 기존 배포 완료 주장은 팀원 기록이며 실제 운영 상태는 이번에 확인하지 않았다. [배포 기준](deployment.md) |

이 선택은 현재 작업 환경에 설치된 도구·OS를 근거로 하지 않았다. Q5의 행사 방 전체, Q13의 브라우저 복원, Q14의 부재 중 보관이 판단 근거다. BLE 직접 전송을 핵심 경로에 추가하면 앱을 닫은 수신자와 이미 떠난 발신자 사이의 보관·전달을 별도로 풀어야 한다. 현재 MVP는 서버 통신으로 구성하며 BLE는 구현 우선순위에서 뺀다. 네트워크 연결이 필요한 서비스라는 점을 시연·소개에도 반영한다. [기존 BLE 조사](technical-findings.md)

초기 SQLite·TypeScript 선택은 실제 main 구현을 비교하기 전의 기술 기본값이었다. 이미 추가된 Redis와 JavaScript 기반을 유지하는 편이 지금의 통합 작업을 줄인다. 저장소를 두 개로 늘리지 않고 Redis 하나에 구현한다. Redis의 원자적 실행은 실패 시 자동 롤백을 뜻하지 않으므로 상태·키 타입·인자를 쓰기 전에 검증한다. 외부 LLM 호출은 원자적 저장 작업 밖에서 수행한다. 저장 성공 뒤 알림을 보내고, 알림 유실은 이력 조회로 복원한다. 구체적인 저장 조건은 [서버 저장 계약](../server/docs/redis.md)을 따른다.

`appendfsync always`는 `everysec`보다 디스크 쓰기 비용이 크다. 응답 시간과 재시작 복원을 검증하며, 성능 문제가 생겨도 사용자에게 이미 성공으로 알린 메시지의 보존 조건을 몰래 낮추지 않는다. AOF와 단일 디스크는 복제·백업·디스크 고장 복구를 보장하지 않는다. 참가 인원별 성능은 실제 부하 검증 전까지 보장하지 않는다. [Redis 영속화](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [FastAPI SSE](https://fastapi.tiangolo.com/tutorial/server-sent-events/)

SSE의 자동 재연결은 저장된 이력의 자동 복원과 다르다. 다음 절차는 SSE 규격과 Q13·Q14를 함께 충족하도록 선택한 설계다. [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)

## 참가자와 데이터 경계

| 데이터 | 다른 참가자에게 제공 | 서버·AI에서의 용도 |
| --- | --- | --- |
| 자기소개 | 입력을 마친 같은 행사 방 참가자에게 제공 | 본인 정보와 추천 입력 |
| 교류 의도 | Q17에 따라 사용자 배너를 누른 상세 화면에 표시. 목록 배너에는 펼치지 않음 | 양쪽 의도를 고려한 추천 입력. 본인은 복원·수정 시 자신의 입력을 확인할 수 있음 |
| 추천 이유 | 상대 상세 화면에서 현재 조회자를 위한 이유를 표시. 숫자 점수 표시는 보류 | 조회자·후보 조합과 양쪽 입력 버전에 대응하는 결과 |
| 참가자 식별자 | 공개 ID는 대상 선택에 사용 가능 | ID를 안다는 이유만으로 해당 참가자의 권한을 부여하지 않음 |
| 브라우저 복원 수단 | 다른 참가자에게 제공하지 않음 | 같은 브라우저를 기존 참가자와 연결. 계정 로그인과 구분하며 상세 발급·보관은 API 계약을 따름 |
| 채팅 메시지 | 같은 대화의 두 당사자에게만 제공 | 행사 종료까지 보관·조회. 현재 추천 입력에 채팅 이력을 추가하지 않음 |
| 행사 종료 정보 | 종료 안내에 사용 | 서버에서 목록·대화 조회·메시지 전송 가능 여부 판단 |

입력 전 목록 API에 개인별 정보를 싣지 않는다. AI 담당은 화면용 참가자 응답을 입력으로 역추정하지 않고, 서버에서 제공한 두 원문과 후보 ID를 받는다. 모델에는 참가자 자유 입력을 데이터로 전달하고, 참가자 본인이 작성한 지시문이 시스템의 추천 규칙을 바꾸지 않도록 처리한다.

입력 화면에는 자기소개와 ‘찾는 사람’을 같은 행사 방 참가자가 상세에서 볼 수 있음을 안내한다. Q10 당시의 AI 전용 안내는 Q17과 맞지 않으므로 사용하지 않는다.

## 화면과 상태 계약

| 화면·조작 | 현재 개발 기준 | 근거 |
| --- | --- | --- |
| 참가자 목록 | 간결한 배너로 표시하고 추천 우선순위를 반영. 교류 의도·추천 이유 전문과 숫자 점수는 목록에 펼치지 않음 | Q9·Q17 |
| 참가자 상세 | 배너를 눌러 이동. 자기소개·그 사용자가 찾는 사람·현재 조회자를 위한 추천 이유·채팅 시작 동작 | Q10을 변경한 Q17, Q11 |
| 내 정보 수정 | 자기소개·교류 의도를 수정·저장. 같은 참가자 ID와 기존 대화 유지, 바뀐 입력을 추천 갱신에 반영 | Q18 |
| 참여 중단 | 목록에서 빠지고 새 메시지 송수신 중단. 기존 대화는 행사 종료까지 열람 | Q18 |
| 참여 재개 | 같은 참가자와 기존 대화로 복귀. 중단 중 거부된 메시지는 사후 전달하지 않음 | Q20 |
| 행사 종료 | 운영자가 수동 종료. 종료 안내로 전환하고 목록·대화 조회와 새 전송 종료 | Q15·Q16 |

목록 정렬·AI 지연의 개발 기본값은 다음과 같다. 유효하게 평가된 참가자는 추천 순서로 먼저 보여주고, 미평가 참가자는 참여 시각·ID의 고정 순서로 뒤에 남긴다. 추천 순서가 같으면 같은 기본 순서로 정렬한다. 서버가 최종 순서를 반환한다. 아직 결과가 없거나 호출이 실패하면 일반 목록과 채팅을 유지하고 AI 상태만 구분해 표시한다. 유효한 추천 이유가 없을 때 상세 화면의 자기소개·교류 의도는 그대로 제공하며 이유를 지어내지 않는다. 이 기본 동작을 만들기 위해 점수 알고리즘을 사용자에게 다시 선택받지 않는다.

| 행사와 참가 상태 | 다른 사람의 목록에 노출 | 새 메시지 송수신 | 본인의 기존 대화 열람 |
| --- | --- | --- | --- |
| 행사 이용 중, 참여 중 | 예 | 가능 | 가능 |
| 행사 이용 중, 참여 중이지만 앱을 닫음 | 예 | 메시지를 보관하고 복귀 시 확인 | 복귀 시 가능 |
| 행사 이용 중, 직접 참여 중단 | 아니오 | 불가. 상대에게 중단 상태를 알리고 새 전송 거부 | 가능 |
| 행사 종료 | 아니오 | 불가 | 불가 |

개발 기본값으로 중단한 참가자도 같은 행사 방의 목록·상세를 조회하고 자신의 입력을 수정할 수 있다. 중단한 상대의 상세를 직접 열거나 기존 대화에서 확인할 때는 중단 상태와 전송 불가를 표시한다. 중단을 프로필 비공개나 기록 삭제로 해석하지 않는다. 재개 버튼을 눌러야 목록 노출과 새 송수신이 돌아온다.

참여 중단 여부는 추천 적합도와 다르다. 낮은 점수·의도 불일치를 중단 상태로 바꾸지 않는다. 입력을 수정했다고 중단 상태를 자동 해제하지 않는다. 상대의 참여 중단 전에 이미 저장된 메시지는 기존 이력에 남기며, 중단 이후의 새 전송 요청을 거부한다.

Q16에 따라 팀이 방과 QR·링크를 미리 준비한다. 참가자는 계정 없이 닉네임·자기소개·교류 의도를 입력한다. 종료 예정 시각과 자동 종료 타이머는 두지 않고 운영자가 수동으로 방을 닫는다. 실제 종료 시각은 서버가 기록하며 닫힌 방을 다시 여는 동작은 MVP에 넣지 않는다.

## 메시지 전달과 복원 계약

1. 참가자 A가 같은 행사 방의 B에게 텍스트를 보낸다. 별도 수락 객체는 만들지 않는다.
2. 서버는 행사 이용 상태·요청 중복·양쪽의 참여 상태 최종 확인과 저장을 같은 트랜잭션으로 처리해 중단·종료와 먼저 확정된 처리를 따른다. 저장이 완료된 뒤 성공을 반환하며 B의 수신·읽음·답장을 의미하지 않는다.
3. 같은 두 참가자의 대화는 같은 대화 ID로 이어진다. 메시지에는 서버 ID·대화별 순번·발신자 요청 ID를 둔다. 행사 이용 중 같은 요청의 재전송은 저장된 메시지를 반환한다. 같은 요청 ID로 수신자나 본문을 바꾸면 충돌 오류다. 행사 종료 후에는 재전송도 열람시키지 않는다.
4. 연결 중인 당사자에게 변경을 알린다. B가 앱을 닫았어도 기록을 삭제하지 않는다. 알림을 놓쳐도 저장된 메시지는 조회할 수 있다.
5. 앱 진입·SSE 재연결 때 서버의 구독 등록 완료 이벤트를 받은 뒤 이력을 조회하고, 그동안 받은 변경 알림도 반영한다. 메시지 순번으로 빠진 이력을 조회하고 서버 메시지 ID로 중복을 제거한다. API 계약의 구독·조회 절차를 프론트와 서버가 함께 따른다.
6. 행사 종료 시 서버가 새 조회·전송을 막고 활성 연결도 종료 처리한다. 프론트는 표시 중인 참가자·채팅 내용을 종료 안내로 전환하고 앱 복귀 시 종료 여부를 재확인한다. 이미 상대가 읽은 내용을 회수한다는 약속은 아니다.

전송 실패가 확인되면 작성한 본문을 유지하고 재시도할 수 있게 하는 구현 기준을 둔다. 이는 확정된 텍스트 대화를 완성하기 위한 처리이며 Q12의 파일·읽음·푸시 보류를 해제하는 결정이 아니다.

이용 종료와 실제 정리를 분리한다. **개발 기본값은 종료 즉시 접근 차단, 종료 1시간 뒤 서비스 DB의 해당 행사 참가자·메시지·추천 원문 정리**다. 정리 작업은 주기 실행과 서버 기동 시 누락 처리를 함께 구현한다. 상세 대상·운영 조건은 API 계약을 따른다. 실제 데이터 삭제를 지금 실행한 것은 아니다.

## AI 담당과의 경계

| 서버가 책임질 것 | AI 담당이 책임질 것 | 함께 고정할 것 |
| --- | --- | --- |
| 같은 행사 방 전체 목록, 참가 권한, 최신 입력, 결과 대상 확인 | 양쪽 의도를 고려한 점수·추천 순서, 산정 방법과 비용·정확성 비교 | 요청 참가자·후보 ID, 입력 버전, 평가 결과와 미평가·실패의 구분 |
| 낮은 평가나 의도 불일치만으로 참가자를 목록에서 제거하지 않음. 참여 중단·행사 종료 조건은 서버가 적용 | 자기소개에 없는 경력·능력을 지어내지 않음. 조회자별 추천 이유 생성 | Q17의 상세 표시와 Q18의 입력 변경 후 결과 갱신 |

입력 변경 시 참가자의 `profile_version`을 갱신한다. 조회자나 후보의 입력 버전이 달라진 결과를 현재 추천 이유처럼 표시하지 않는다. 같은 행사 방에서 후보가 추가·변경·중단·재개되면 후보 집합의 버전도 갱신해 오래된 순위를 구분한다. 전체를 매번 다시 호출할지, 영향을 받은 결과만 갱신할지는 AI 담당이 정확성과 효율을 비교해 정한다.

숫자 점수는 내부 평가에 사용할 수 있지만 현재 화면 응답의 필수 필드로 만들지 않는다. 프론트·서버는 추천 순서·평가 상태·이유·입력 버전을 공유하고 모델·캐시·후보 평가 전략은 AI 담당의 결정 범위로 유지한다.

## 공통 API 기준

경로·필드·오류·메시지 순번·SSE 이벤트·AI 입출력은 [API 계약](api-contract.md)을 따른다. 현재 파일과 별개로 같은 계약을 각 담당이 다시 정의하지 않는다. 화면용 응답은 참가자의 자유 입력을 실행 가능한 HTML로 렌더링하지 않으며, 공개 ID는 권한 증명으로 사용하지 않는다.

[검증 계획](validation.md)의 V01~V12를 핵심 흐름의 완료 조건으로 사용한다. 추천 평가 E01~E08은 AI 담당과 검증 담당이 함께 검토한다. 숫자 점수 자체를 품질 검증으로 사용하지 않는다.

## 첫 통합 작업과 완료 증거

아래는 현재 계약을 구현할 첫 개발 작업이다. 김성빈 외 실제 담당자 배정은 [분업안](team-plan.md)에서 추후 정한다.

| 작업 | 소유 경계 | 완료 증거 |
| --- | --- | --- |
| 공통 예시와 계약 고정 | 프론트·서버·AI 공동, 서버 담당이 API 통합 | 같은 입력·참가자·메시지·추천 예시를 각 담당의 코드에서 사용 |
| 참여·목록·상세 | 김성빈 / 서버 담당 | 서로 다른 두 브라우저의 실제 입력을 목록에서 확인하고 배너를 눌러 상세 소개·교류 의도·추천 이유 확인. 입력 전 개인별 정보는 반환하지 않음 |
| 채팅·수정·중단·복원·종료 | 김성빈 / 서버 담당 | 실제 답장·입력 수정·참여 중단·브라우저 재실행·부재 중 전송·행사 종료 후 접근 종료를 각각 재현 |
| 실제 추천 | AI 담당 / 서버 호출 / 프론트 표시 | 예시 추천을 실제 모델 출력으로 교체하고 의도 변경·충돌·정보 부족 사례의 결과와 비용·시간 기록 |
| 검증·발표 | 검증·시연 담당, 구현 담당 리뷰 | 실제 두 사용자 실행 기록, AI 비교 결과, 5분 발표와 백업 영상. 가짜 데이터 실행과 실제 참가자 관찰 구분 |

첫 통합에서 예시 추천 응답을 쓰더라도 실제 AI가 동작했다고 기록하지 않는다. 대화 양쪽이 실제로 메시지를 보낸 경우와 일방 전송을 구분한다. 시연 기기·내부 마감 미정은 담당자 배정 시 확인할 실행 조건이며, 부가 기능 논의로 대체하지 않는다.

Q19에서 추천 비교·실제 답장·운영진 도입 가설과 대시보드 보류를 선택했다. 검증 담당은 사람의 기대 결과를 먼저 적은 사례와 실제 모델 결과를 비교하고, 입력·송신·수신·답장을 구분해 관찰한다. 실제 대면은 별도 관찰이며 채팅 건수로 대체하지 않는다. 세부 사례와 발표 배점 연결은 [평가 계획](topic-evaluation.md)을 따른다.

## 개발 시작 시 확인할 실행 조건

제품 질문은 마쳤다. 다음은 제품 선택을 다시 묻는 항목이 아니라 담당자가 첫 작업에서 확인할 실행 조건이다.

- 김성빈 외 서버·AI·검증 역할의 실명 배정과 두 시연 기기의 브라우저.
- HTTPS 배포 위치·영속 디스크와 운영자 자격 증명.
- 행사 제공 AI 게이트웨이 또는 팀이 사용할 모델의 실제 호출 권한·예산.
- 첫 통합·실기기 검증·녹화·발표 준비의 내부 시각.

기존 `web/package-lock.json`·`server/uv.lock`을 사용해 실행을 재현하고 의존성 변경 시 잠금 파일도 갱신한다. 설치된 현재 환경을 스택 선택 근거로 사용하지 않는다. [팀 작업 목록](team-plan.md)과 [검증·시연 계획](validation.md)을 따라 실행하며, 완료를 실제 동작 근거로 기록한다.
