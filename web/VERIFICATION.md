## 브라우저에서 눌러본 것

개발 서버를 375×812 모바일 뷰포트에서, 저장소를 비운 상태로 시작해 확인했다.

- 첫 실행: 설치 등록 → 소개 입력 → 저장 → `#nearby`. **발견은 꺼진 채로 시작**하고
  "주변 발견 켜기"가 주 동작으로 보인다(계약대로 신규 설치는 `discovery_enabled: false`).
- 발견 켜기: 데모 라디오가 스캔 → 관측 보고 → 45명 표시. 패널에
  "예시 데이터로 보여드리는 화면이에요. 실제 BLE 발견이 아니에요."가 함께 표시됨
- 추천: "AI 추천은 아직 준비 중이에요."로 표시됨(v0.1은 항상 `unavailable`)
- 상세 → 메시지 보내기 → 전송 성공(말풍선 1개)
- **발견 끄기**: 주변 0명 + "주변 발견이 꺼져 있어요", 대화 목록은 유지되고
  상대에 "주변에 없음" 배지가 붙음
- **발견이 꺼진 상태에서 기존 대화**: 입력창이 열려 있고 전송 성공(말풍선 2개, 오류 없음)
- **발견이 꺼진 상태에서 새 상대**: 입력창 비활성화 + "주변 발견을 켜면 새 대화를 시작할 수
  있어요.", 상세는 "지금은 주변에 없어요"
- **재실행 복원**: 새로고침 후 입력 화면으로 되돌아가지 않고 같은 설치 사용자로 복원.
  대화와 꺼둔 발견 상태가 그대로 유지됨
- 레이아웃: 375px와 320px 모두 `scrollWidth === clientWidth`로 가로 넘침 없음
- 콘솔 오류 0건

주의: 자동화 도구로 보낸 합성 클릭·키 입력은 일부가 대상 요소에 전달되지 않는다. 실제 이벤트가
요소에 도달하면 동작하므로, 자동화 실패를 앱 버그로 기록하지 않는다.

## 실제 서버와의 연동 (2026-09-20)

**데모가 아니라 실제 FastAPI·Redis 서버를 상대로 확인했다.** 브라우저 탭 두 개가 두 기기를
대신했고([dev-radio.js](src/api/dev-radio.js), `VITE_DEV_RADIO=1`), 서버는 `server/`의 구현이다.

```sh
cd server && docker compose up -d --wait redis && uv run fastapi dev app/main.py
cd web && VITE_USE_MOCK=0 VITE_DEV_RADIO=1 npm run dev
# 탭 A: /?device=a   탭 B: /?device=b
```

- 탭 A: `POST /api/v1/installations` → 201, `GET /api/v1/me` → 200 (네트워크 로그로 확인)
- 두 탭이 각각 소개를 저장하고 발견을 켬
- 탭 B가 **탭 A를 발견**: `POST /discovery/identifiers` → 광고 → `POST /discovery/observations`
  → 목록에 "성빈 / 백엔드 API를 만들고 있어요." 표시
- 탭 B가 상세를 열고 **첫 메시지 전송** → 201
- 탭 A의 대화 목록에 도착 → **답장 전송**
- 탭 B가 다시 들어오니 두 메시지 모두 표시 (`나: …`, `성빈: …`)

즉 **등록 → 프로필 → 발견 → 관측 → 첫 메시지 → 답장 → 복원**이 실제 HTTP로 한 바퀴 돌았다.
프론트 호출부와 서버 응답이 실제로 맞는다는 근거다. 다만 이것은 **BLE 검증이 아니다.**
식별자 교환을 브라우저 두 탭이 `localStorage`로 대신했을 뿐이다.

한 가지 관찰: 미리보기 패널의 탭은 `document.visibilityState`가 계속 `hidden`으로 보고돼
15초 폴링과 복귀 동기화가 눌린다. 이는 "안 보이는 화면은 폴링하지 않는다"는 설계대로이며,
그 상태에서도 서버에는 두 메시지가 모두 저장돼 있었고(직접 조회로 확인) 화면을 다시 열면
그대로 나타났다. 앱 버그로 기록하지 않는다.

## 자동 테스트가 덮는 범위

`tests/`는 Node 내장 러너로 계약과 경합을 검증한다(44개).

  자격 증명이 없으면 요청 자체가 나가지 않는 것, 프로필 전체 교체와 발견 상태 POST,
  `after_seq` 전진 전용 이력과 경로 인코딩, `{error:{code,message,details.field}}`를 필드
  오류로 변환, 계약 오류 코드의 한국어 문구, HTML 응답·시간 초과·취소,
  그리고 **`getNearby`·`getPerson`·`subscribe`가 존재하지 않는 것**

  서버가 준 권한 창 기준의 첫 메시지 가능 여부, `unavailable`을 근거 부족으로 오해하지 않는
  선택적 안내, 참여 의사와 라디오 상태의 분리
- `controller.test.js`: 설치 1회 등록과 복원, 프로필 없는 신규 설치의 첫 화면,
  **주변 목록이 조회가 아니라 네이티브 관측 보고로 도착하는 것**, 푸시된 관측의 즉시 반영,
  관측 캐시에서 읽는 상세와 이탈 처리, 프로필 전체 저장, 서버 필드 오류의 입력 연결,

  사라진 상대에게 첫 메시지 실패, 같은 키 재시도로 메시지 1건만 저장, 늦은 전송이 다른 대화에

  부트 실패 화면, 401 시 세션 초기화, 중복 저장 잠금,
  **라디오가 막혀도 참여 설정을 스스로 끄지 않음**

## Android APK와 실제 서버 (2026-09-20)

[네이티브 계층](../android/README.md)을 구현하고 에뮬레이터(API 36)에 설치해 **APK가 실제
FastAPI 서버와 통신하는 것까지** 확인했다.

- 앱 실행 → `POST /api/v1/installations` 201 → `GET /me` 200
- 소개 저장 200, 발견 켜기 200
- **네이티브 스캐너가 `POST /api/v1/discovery/identifiers` 200을 직접 호출**. WebView와 다른
  소켓에서 나갔으므로 네이티브가 보호 저장소의 자격 증명으로 스스로 인증한 것이 맞다
- foreground service가 실제로 시작되고, 플러그인 상태
  (`bluetooth: on`, `permission: granted`, `os: restricted`)가 화면에
  "배터리 절약 설정 때문에 백그라운드 발견이 제한될 수 있어요."로 표시됨

이 과정에서 두 가지를 발견해 고쳤다. 둘 다 실제로 돌려보지 않으면 나오지 않는 문제다.

1. **서버 CORS에 `https://localhost`가 필요하다.** Capacitor WebView의 출처는 API 호스트가
   아니라 `androidScheme`이라 preflight가 400으로 막혔다.
2. **`http://10.0.2.2`는 mixed content로 차단된다.** `https://localhost` 페이지에서 http를
   부르기 때문이다. `adb reverse` + `http://localhost`는 secure origin 예외라 통과한다.

**광고 → 스캔 → 관측 보고 → 서버 조회 → 첫 메시지 → 답장**이 실제 무선과 실제 서버로 한 바퀴
돌았다. 자세한 내용과 여기서 고친 두 가지는 [android/README.md](../android/README.md)에 있다.

## 아직 검증하지 못한 것

- **배포 환경.** 위 검증은 `adb reverse`로 개발 PC의 서버에 붙인 것이다. 공용 HTTPS 서버로
  올린 뒤의 왕복은 아직이다
- 백그라운드·화면 꺼짐 상태의 발견. 두 대 모두 앱을 앞에 둔 채로만 확인했다.
  실기기가 `os: restricted`를 보고하므로 시연 전 배터리 최적화 제외가 필요하다
- 거리에 따른 발견 성공률, 여러 대가 동시에 있을 때의 동작
- Bluetooth OFF·권한 거부 상태의 화면. 그 상태를 만들어보지 않았다
- Redis 재시작·AOF 복원의 실제 장애 시나리오(V12). 앱 인스턴스 재시작만 확인했다
- 부하·동시성 규모. 원자성은 검증했지만 성능은 측정하지 않았다
- AI 추천 품질·지연. v0.1에는 추천 자체가 없다
- 릴리스 서명. `assembleRelease`는 통과하지만 서명 설정은 하지 않았다
