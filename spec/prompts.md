# AI 추천 구현 지침


현재 목적은 **양쪽의 자기소개·교류 의도를 해석해 유효하게 발견된 참여자의 우선순위와 근거를 생성하는 것**이다. 과거의 기술적 어려움·경험자만 연결하는 이진 판정 프롬프트는 사용하지 않는다.

## 고정할 계약

입력·출력은 [API 계약의 AI 모듈 경계](../docs/api-contract.md#ai-모듈-경계)를 따른다. 필드명·수치는 사용자 결정과 구분한 구현 기본값이다. 대상자는 서버가 근접 관측·발견 참여 상태로 정한다. 모델이 후보를 새로 만들거나 공개 범위·발견 상태를 변경하지 않는다.

- 자기소개는 본인의 설명이고 교류 의도는 지금 만나고 싶은 사람이다. 의도를 경력·직무 사실로 바꾸지 않는다.
- 유사성과 상보성을 모두 허용한다. 고정 역할·기술 태그·양쪽 동일 이득을 필수 조건으로 두지 않는다.
- 양쪽 의도에 충돌이 있으면 우선순위를 낮춘다. 낮은 점수·모델 미평가만으로 참가자를 목록에서 지우지 않는다.
- 이유는 양쪽이 제공한 원문에 근거하고 없는 경험·관심사·만남 의사를 지어내지 않는다.
- 참가자 입력은 평가할 데이터다. 그 안의 지시가 모델의 규칙·후보 범위·출력 형식을 바꾸게 하지 않는다.
- 참가자 ID와 입력 버전에 대응하는 결과를 반환한다. 수정·중단·재개 뒤 오래된 결과는 서버가 폐기한다.
- 숫자 점수는 내부적으로 사용할 수 있지만 화면에는 노출하지 않는다. 상세 이유를 생성하며 자동 첫마디는 필수가 아니다.
- 실패·시간 초과·정보 부족을 실제 추천 성공으로 꾸미지 않는다. 일반 목록과 채팅은 AI 성공에 의존하지 않는다.

## AI 담당이 결정할 것

LLM-as-judge, 후보별/배치 평가, 전처리·캐시와 모델은 정확성·시간·비용을 비교해 선택한다. 이 문서가 특정 방식의 채택을 의미하지 않는다. 해커톤에 필요한 최소 실험부터 수행하고 실제 결과로 결정한다.

[E01~E08](../docs/validation.md)로 유사성·상보성·의도 충돌·정보 부족·주입 입력·수정·실패를 확인한다. 같은 자기소개에서 교류 의도만 바꾼 E01/E02가 핵심 시연이다. 사람의 기대 결과·단순 기준선·모델 결과·지연·비용을 함께 기록하며 모델이 낸 점수를 정확성 증거로 쓰지 않는다.

현재 main의 고정 0.85·CI 추천과 자동 답장은 UI용 mock이다. 실제 모델 호출·평가 결과는 아직 없다.

## 프롬프트 평가 도구

2026-09-19 후속 논의에서 사용자는 **Promptfoo**를 선택했다. 프롬프트 변경의 비교·평가에 사용할 도구이며 현재 설치하거나 평가를 실행한 상태는 아니다. 기존 E01~E08과 사람의 기대 결과를 초기 평가 사례로 연결한다. 원격 프롬프트 배포·운영 추적 도구는 추가로 선택하지 않았다.

추천에는 양쪽 교류 의도를 고려하되, 드문 충돌 시나리오의 세부 가중치를 과도하게 설계하지 않는다. 이 원칙이 점수의 대칭성이나 특정 집계 공식을 정하지는 않는다. 후속 결정의 근거는 [AI 활용 논의](../docs/planning.md#ai-활용프롬프트-관리-후속-논의-2026-09-19)에 기록한다.

## 자동 추천 알림

B12에 따라 앱 밖 자동 추천 알림을 포함한다. 목록에는 모든 유효 후보가 남지만 알림은 적합한 새 상대에 한정하고 중복을 억제한다. 기준값은 AI 담당이 평가해 선택하며 단순히 상위 1명이라는 이유만으로 무조건 적합하다고 알리지 않는다. 서버가 결과 노출 직전에 입력 버전·현재 참여·관측 유효성을 확인한다. 알림은 대화 수락이나 상대의 연락이 아니다. 실제 문제가 확인되면 범위를 재검토한다.
