# 버전 로드맵

> 원칙: **모든 버전이 이전 버전을 깨지 않는다.** 웹이 항상 최소 공통 분모로 남는다.
> BLE는 웹을 대체하지 않고 **얹힌다.**

| | 버전 | 플랫폼 | 근접 판정 | 언제 |
|---|---|---|---|---|
| **v0.1** | 해커톤 제출본 | 웹 PWA | QR 방 코드 | **오늘 밤** |
| **v0.2** | 첫 판매본 | 웹 PWA | QR + 구역 선택 | +1~2주 |
| **v0.3** | 정밀도 확장 | 웹 + 안드로이드 래핑 | QR + **BLE** | +2~4주 |
| **v1.0** | 상시 모드 | 웹 + 양 플랫폼 | BLE 자동 입장 | +2~3개월 |

## v0.1 — 웹 PWA + QR (해커톤 제출본)

**목적**: 제품이 성립함을 증명하고 심사에서 점수를 받는다.

**범위 — 없으면 제품이 아닌 것**
1. QR·코드로 방 입장 + 닉네임·소속
2. 상태 선택 + 한 줄 입력 (30초 안에)
3. 방 목록 — 상단 집계 + 카드 리스트
4. **AI 접점 매칭 + 카드** (상보 관계 + 근거 + 첫마디)

**범위 — 점수에 직결**
5. 운영진 대시보드 (숫자 하드코딩 가능)
6. 넘어간 정보 / 안 넘어간 정보 대조 화면
7. 접점 없을 때 화면

**안 하는 것**: BLE, 로그인, DB, 채팅, 푸시, 일상 모드

> **채팅은 특히 넣지 말 것.** 넣는 순간 근거리 채팅 앱이 된다.
> "앱에서 채팅하지 않고 현실에서 말을 건다"가 차별점이다.

**기술**: FastAPI 또는 Next.js + 메모리 dict + SSE. LLM은 국민대 게이트웨이.
**예상**: 3명 × 10~12시간
**얻는 것**: 심사 통과. 설치 없이 3초 입장이라는 최강 무기.
**리스크**: 게이트웨이 장애 → 녹화 영상과 사전 생성 로그 폴백 준비

## v0.2 — 첫 유료 판매본

**목적**: 주최자에게 실제로 팔 수 있는 최소 형태.

**추가**
1. **구역 선택** — 무대 앞, 음료 테이블, 창가, 로비. BLE 없이 위치 맥락 확보
   → 카드가 "음료 테이블 쪽 민서님"으로 바뀐다. 사람 찾을 때 좌표보다 랜드마크가 유용하다
2. **상태 세트 커스텀** — 운영진이 행사 성격에 맞게 편집 (해커톤형 / 밋업형 / 직접 작성)
3. **참가자 배지** — 연사, 스태프, 스폰서 표시
4. **종료 후 PDF 리포트** — 입장률, 접점 수, 대화 시작 수, 인기 주제. **재계약의 근거**
5. 상태 만료 실제 동작 + 하트비트

**예상**: +1~2주
**얻는 것**: 행사당 30~50만원 과금 가능. 대시보드와 리포트가 지불 이유다.
**리스크**: 구역을 너무 잘게 나누면 입력 비용이 늘어난다. 4~6개로 제한할 것

## v0.3 — 안드로이드 래핑 + BLE (가장 영리한 BLE 경로)

**핵심 아이디어**: 웹을 버리지 않는다. **웹 코드를 그대로 안드로이드 앱으로 감싸고 BLE만 네이티브로 붙인다.**

```
아이폰 사용자  →  웹 (QR 입장, 구역 선택)        ← 계속 동작
안드로이드     →  앱 (같은 웹 코드 + BLE 근접)    ← 정밀도 향상
                    ↓
              같은 서버, 같은 방, 같은 매칭
```

**방법**: Capacitor로 웹 프로젝트를 안드로이드 앱으로 빌드. `@capacitor-community/bluetooth-le` 플러그인으로 BLE만 네이티브 처리. **웹 코드 재사용률 100%.**

**BLE로 하는 것 (그리고 하지 않는 것)**
- **한다**: 짧은 ID만 광고하고 스캔. 서버에서 ID를 프로필로 해석
- **안 한다**: BLE로 데이터를 실어 보내는 것. **광고 페이로드가 31바이트라 한글 여섯 자면 끝난다**
- 결과: 카드에 "3m 근처" 표시. 구역 선택보다 정밀

**필수 설계 — 실패해도 죽지 않을 것**
- BLE가 안 잡히면 자동으로 QR·구역 방식으로 강등(graceful degradation)
- BLE는 **정밀도 향상 기능**이지 입장 수단이 아니다

**예상**: +2~4주 (대부분 BLE 디버깅과 기기별 테스트)
**얻는 것**: 대형 행사에서 "이 넓은 홀에서 누가 가까운가"가 실제 가치가 됨. 기술 차별화.
**리스크**: 안드로이드 12+ 권한(BLUETOOTH_SCAN, ADVERTISE), 기기별 편차, 실기기 테스트 필수

## v1.0 — 상시 모드

**목적**: 설치 기반이 쌓인 뒤에야 의미가 생기는 것들.

**추가**
1. **BLE 자동 입장** — QR을 안 찍어도 행사장에 들어가면 자동 인식
2. **iOS 앱** — 제약을 안고 감. 백그라운드에서 서비스 UUID가 오버플로 영역으로 가고 안드로이드에서 안 보이는 문제를 우회 설계
3. **일상 모드(PLACE)** — 캠퍼스 건물, 도서관, 학생식당. **밀도가 있는 공간만**
4. 신뢰도·이력 — 반복 참가자 인식, 과거 접점 기억

> **순서가 중요한 이유**: BLE 자동 발견은 설치 기반이 먼저 있어야 한다.
> 아무도 앱을 안 깔았는데 자동 발견을 하면 발견할 사람이 없다.
> Highlight와 Sonar가 정확히 이 순서를 거꾸로 했다가 죽었다.

**예상**: +2~3개월
**리스크**: 여기서부터 근거리 소셜 무덤의 실패 모드가 다시 살아난다. 밀도와 수익모델을 계속 지켜야 한다
