## 0. QR과 BLE는 서로 다른 일을 한다 (발표에서 그대로 쓸 것)

| | 하는 일 | 성립 조건 |
|---|---|---|
| **QR** | *어느 무리*인지 자른다 — 이 행사, 이 장소에 온 사람 | 행사가 있어야 함 |
| **BLE** | *얼마나 가까운지* 판단한다 | 행사 없이도 됨. 아무 데서나 |

QR만 있으면 행사가 없는 날은 아무것도 못 한다.
BLE만 있으면 누가 같은 행사에 온 사람인지 모른다. **둘 다 필요하다.**

### BLE를 고른 이유는 정밀도가 아니라 프라이버시다

GPS는 내 좌표가 서버로 올라간다. 서버가 그 좌표를 받아 "둘이 가깝네"를 계산한다.
그러려면 **서버가 내가 어디 있는지 알아야 한다.** 그게 싫은 사람이 있다.

BLE는 그 계산을 서버가 하지 않는다. 내 기기가 "지금 내 전파가 닿는 사람"만 본다.
가깝다는 판단이 기기 안에서 끝나므로 **서버에 올라갈 좌표 자체가 생기지 않는다.**

> 발표 멘트: "GPS를 쓰면 여러분 위치가 저희 서버로 옵니다.
> 블루투스는 그 계산을 폰 안에서 끝냅니다. 저희 서버에는 올라갈 좌표가 없습니다."

"정밀도가 좋아서"라고 말하지 말 것. 그러면 "GPS가 더 정확한데요"에 진다.

### 근접 판정은 서버에 묻지 않는다

BLE로 잡은 짧은 ID를 서버에 보내 "이게 누구냐"고 물으면,
서버는 좌표는 몰라도 **누가 누구 옆에 있었는지는 알게 된다.** 좌표만 안 보내면 되는 게 아니다.

QR로 방에 들어온 시점에 이미 그 방 명단을 받아놨다.
그러므로 **ID 해석은 기기 안에서 한다.** 근접 판정에 서버 왕복이 없다.

> 정해두지 않으면 구현할 때 자연스럽게 서버 호출로 짜게 된다. 그래서 규격에 박아둔다.

### 그래서 웹만으로는 안 되고 Capacitor가 필요하다

아래는 **BLE를 버릴 이유가 아니라 네이티브로 감쌀 이유**다.

1. **Web Bluetooth에는 광고(advertising) API가 없다.** GATT 클라이언트 역할만 지원한다. 웹만으로는 내 기기가 존재를 뿌릴 수 없다.
2. **iOS 사파리는 Web Bluetooth를 지원하지 않는다.**
3. 네이티브로 가더라도 **iOS는 백그라운드에서 서비스 UUID를 오버플로 영역으로 옮기고 로컬 이름을 버린다.** 그 영역은 같은 UUID를 명시해 스캔하는 iOS 기기만 읽는다. **안드로이드에서는 백그라운드 아이폰이 안 보인다.**

→ 1·2번은 Capacitor + peripheral 지원 플러그인으로 넘는다.
→ 3번은 남는 제약이다. **아이폰은 웹으로 받는다.** BLE만 빠지고 나머지는 전부 동작한다.
→ **BLE가 안 잡혀도 QR 방은 그대로 돈다. BLE는 입장 수단이 아니다.**

## 0-1. 방 두 종류 (코드는 같고 정책만 다르다)

| | **EVENT (행사)** | **PLACE (일상)** |
|---|---|---|
| 누가 만드나 | 운영진이 생성 → 코드·QR 발급 | 상시 개방. 장소 이름으로 존재 |
| 예시 | `KOSS26` 코쓱톤 네트워킹 | `국민대 미래관 4층`, `중앙도서관 3열람실` |
| 종료 | 운영진이 정한 종료 시각 | 없음. 개인 상태만 만료 |
| 상태 세트 | 행사 유형별 커스텀 | 기본 5종 고정 |
| 대시보드 | **있음 (유료 기능)** | 없음 |
| 참가자 배지 | 운영진이 부여 가능 (연사, 스태프, 스폰서) | 없음 |
| 밀도 확보 | **운영진 공지 한 번** | 장소에 QR 스티커. 느림 |

**구현 차이는 `room.type` 필드 하나와 만료 정책뿐이다.** 나머지 로직은 공유한다.

> **발표 전략**: 시연과 문제 정의는 **EVENT 하나로만** 간다.
> PLACE는 마지막 한 컷과 확장 슬라이드 한 장으로만 등장시킨다.
> 이유: 일상 근거리 소셜은 심사위원에게 무덤을 연상시키고, "주최자가 낸다"는 최선의 방어가 희석된다.

## 1. 데이터 모델 (Redis 기반; 도메인 저장은 후속 구현)

```python
rooms = {
  "KOSS26": {
    "type": "EVENT",            # EVENT | PLACE
    "title": "코쓱톤 네트워킹",
    "when": "국민대 미래관 4층 · 오늘 18:00까지",
    "ends_at": ...,             # EVENT만. PLACE는 None
    "status_set": "HACKATHON",  # 아래 2번. EVENT는 운영진이 선택

    # 행사마다 소속의 성격이 다르다. 코드에 박지 않는다.
    #   대학 행사 -> 학교 목록      밋업 -> 회사 자유 입력      사내 -> 팀 목록
    "affiliation": {
      "label": "소속",                                   # 소속 / 회사 / 팀 / 학교
      "options": ["국민대", "숭실대", "순천향대"],        # None이면 자유 입력
      "placeholder": "직접 입력"
    },
    "created_at": ...,
    "members": {
      "<ephemeral_id>": {
        "nick": "지원",
        "school": "국민대",        # 선택
        "status": "LOOKING_FOR",    # 아래 4종 (2번)
        "note": "GitHub Actions 배포에서 권한 오류로 막힘",   # 자유 한 줄, 140자
        "tags": ["React", "배포", "CI"],   # LLM이 note에서 추출
        "last_seen": ...,
        "opt_in_match": true
      }
    }
  }
}
```

**만료 규칙**
- 하트비트 **60초** 간격. **5분** 끊기면 목록에서 제거
- 방을 나가면 즉시 삭제
- Redis AOF와 볼륨으로 재시작 후 복구. 상태 TTL·퇴장·행사 종료 삭제는 후속 API에서 구현하며, TTL은 디스크 기록의 즉시 완전 삭제를 보장하지 않음
- `ephemeral_id`는 브라우저 세션마다 새로 생성. 계정 없음

> **2026-09-19 정정 — 위 마지막 줄이 느슨했다.** "세션마다"가 정확히 뭘 뜻하는지
> 안 정해져 있어서, 구현하기 나름으로 "새로고침할 때마다 남처럼 다시 입장"이
> 될 수 있었다(실제로 그렇게 만들었다가 실기기에서 잡음). 아래로 정확히 정의한다.

## 1-1. 새로고침·재시작·행사 종료 — 셋은 다른 사건이다

| 사건 | 나(참가자)한테 어떻게 보이나 | 메커니즘 |
|---|---|---|
| **새로고침** (F5, PWA 재개) | **유지된다.** 그대로 방으로 돌아간다 | `ephemeral_id`를 `sessionStorage`에 둔다. 탭이 살아있는 동안 클라이언트가 그 id로 "나 맞죠?"(`GET /room/{code}/me`류)를 다시 묻는다 |
| **탭·앱을 완전히 닫음** | **사라진다.** 다시 열면 처음 온 사람 | `sessionStorage`는 탭이 죽으면 브라우저가 알아서 지운다. 서버가 뭘 안 해도 된다 |
| **새 탭에서 같은 링크를 염** | **처음 온 사람.** 이전 탭과 별개 | `sessionStorage`는 탭마다 독립이라 기본적으로 이렇게 된다. 의도한 동작이다 |
| **하트비트 5분 끊김** | 목록에서 사라진다 (이미 있던 규칙) | 새로고침으로 살아있다는 신호를 계속 주지 않으면(하트비트 실패) 자연 만료 |
| **행사 종료** (`ends_at` 지남) | 입장·조회·매칭이 전부 막히고 "행사가 끝났습니다" 화면만 보인다 | 아래 1-2번 |
| **서버 재시작** | 전부 새 사람 (완전 초기화) | `rooms` 딕셔너리 자체가 새로 생성된다. 이것만 진짜 "DB 없음"의 의미다 |

**`sessionStorage`엔 id 하나만 둔다.** 이름·소속·한 줄 같은 실제 내용은 안 넣는다 —
저장하는 순간 "계정 없음" 약속이 흐려진다. id만으로는 아무 의미가 없고, 서버가
그 id를 아직 기억하고 있을 때만 값어치가 생긴다.

## 1-2. 행사 종료는 누가 판단하나

**사람이 그 순간 누르는 버튼이 아니다.** 운영진이 방을 만들 때 `ends_at` 시각을
한 번 정한다(이미 있는 필드, 예: "오늘 18:00까지"). 그 뒤론 서버가 매 요청마다
`now > ends_at`인지 **그냥 비교만 한다.** 크론이나 스케줄러, 백그라운드 스윕
전혀 필요 없다.

**"방이 소멸한다"는 것도 두 층위로 나뉜다:**
- **참가자가 보기엔**: 자동이고 즉시다. `ends_at`이 지난 순간부터 입장·조회·매칭
  전부 "행사 종료" 응답만 온다
- **서버 메모리엔**: 그 순간 물리적으로 지워지는 게 아니다. `rooms[code]`는
  서버가 재시작될 때까지 RAM에 남을 수 있다 — 다만 접근이 다 막히니 사용자
  입장에선 차이가 없다. 완전한 회수는 서버 재시작(위 표) 또는 각자의 5분
  하트비트 만료로 자연히 일어난다

**나중에 "운영진이 일찍 끝내고 싶다"가 필요해지면**, `ends_at`을 그 순간의
과거 시각으로 덮어쓰는 것으로 충분하다. 메커니즘은 안 바뀐다.

## 2. 상태 세트

> **2026-09-19 정정**: 이 절이 프로토타입과 어긋나 있었다(`NEED_HELP`/`CAN_HELP`/`BREAK`/`FOCUS` vs
> 프로토타입의 `LOOKING_FOR`/`CAN_SHARE`/`FIRST_TIME`/`OPEN`). 프론트가 이미 891줄로 구현·검증된
> 쪽을 기준으로 통일한다. **아래가 이번 제출의 유일한 상태 세트다.**

| 코드 | 라벨 | 뜻 | 입력 placeholder 예시 |
|---|---|---|---|
| `LOOKING_FOR` | 이런 분 찾아요 | 도움이 필요함. note 사실상 필수 | "배포·CI 경험 있으신 분 찾아요" |
| `CAN_SHARE` | 이런 얘기 할 수 있어요 | 도와줄 수 있음 | "작년에 도커로 CI 파이프라인 구축해봤어요" |
| `FIRST_TIME` | 처음 왔어요 | 혼자 왔음. 아무나 이어줘도 됨 | "혼자 왔어요. 기획하다가 백엔드가 궁금해졌어요" |
| `OPEN` | 대화 가능 | 제약 없음 | "뭐든 편하게 말 걸어주세요" |

**매칭 재료는 `LOOKING_FOR` × `CAN_SHARE`.** `FIRST_TIME`끼리도 이어준다.
HACKATHON·MEETUP 두 방 모두 이 4종을 쓴다. 행사마다 달라지는 건 상태 세트가 아니라
2-2번의 `affiliation`(소속 라벨·입력 방식)이다 — 프로토타입 `ROOMS` 객체가 그 증거다.

> 아래는 예전 5종(`OPEN`/`FOCUS`/`BREAK`/`NEED_HELP`/`CAN_HELP`)의 흔적이었다.
> **PLACE(일상 모드)는 이번 제출 범위 밖**이므로(8번 "자를 순서" 1위) 상태 세트도 정하지 않는다.
> PLACE를 만들 때 새로 설계한다.

## 2-2. 행사마다 달라지는 것 — 코드에 박지 말 것

| 항목 | 해커톤 | 밋업·컨퍼런스 | 사내 행사 |
|---|---|---|---|
| 방 제목 | 코쓱톤 네트워킹 | 서울 프론트엔드 밋업 | 신입 온보딩 데이 |
| 소속 라벨 | 소속 | 회사 | 팀 |
| 소속 입력 | 학교 목록 + 직접 입력 | 자유 입력 | 부서 목록 |
| 상태 세트 | HACKATHON | MEETUP | ONBOARDING |

**학교 세 개를 코드에 박으면 이 대회 전용 데모가 된다.**
프로토타입은 `ROOMS` 객체 하나로 이걸 증명한다. 데모 메뉴의 "다른 행사로"를 누르면
같은 코드가 회사 자유 입력으로 바뀐다. **발표에서 이 전환을 보여줄 것.**

## 2-1. 운영진 대시보드 (제품의 절반, 그리고 유일한 매출원)

주최자가 돈을 내는 이유는 **참가자 만족도를 숫자로 보고해야 하기 때문**이다.

```
코쓱톤 네트워킹 · 실시간

  입장       64명 / 참가자 90명 (71%)
  상태 설정  58명 (91%)
  접점 발견  37건
  대화 시작  24건        ← "좋아요" 누른 수
  ─────────────────────────
  가장 많은 요청 주제
    1. 배포·CI        9건
    2. 기획           6건
    3. 디자인         4건
```

행사 종료 후 PDF 리포트 1장. **이게 재계약 이유다.**
참가자 리텐션이 아니라 **주최자 재도입**이 지표라는 점을 발표에서 명시할 것.

## 3. 화면 (3개면 충분)

**A. 입장** — QR 또는 코드 6자리 → 닉네임 → 상태 선택 → note 한 줄. **30초 안에 끝나야 한다.**

**B. 방** — 상단에 집계 `찾는 중 3 · 나눌 수 있음 1 · 처음 2`, 아래에 카드 목록.
내 상태는 언제든 한 탭으로 변경.

**C. 접점 알림** — AI가 접점을 찾으면 카드가 뜬다.
```
💡 3m 근처에 민서님이 있습니다
   민서님은 작년에 도커 CI를 구축해봤습니다.
   지금 막히신 배포 권한 문제, 물어볼 만합니다.

   첫마디 → "민서님, 혹시 Actions 배포 권한 쪽 해보셨어요?"
   [ 좋아요 ]  [ 괜찮아요 ]
```

## 4. AI 레이어 (여기가 AI 활용성 15점)

### 4-1. note → tags 추출 (입력 비용을 없애는 부분)
사용자는 한 줄만 쓴다. LLM이 기술 태그, 문제 유형, 난이도를 뽑는다.
```
입력: "GitHub Actions 배포에서 권한 오류로 막힘"
출력: { "tags": ["GitHub Actions", "CI/CD", "배포", "권한"], "kind": "STUCK", "level": "mid" }
```

### 4-2. 접점 찾기 (핵심)
방 안의 `LOOKING_FOR` × `CAN_SHARE` 쌍을 LLM에 넣고 **상보 관계**를 찾는다.

```jsonc
{
  "match": {
    "helper": "<id>",
    "seeker": "<id>",
    "type": "ASYMMETRIC_HELP",     // ASYMMETRIC_HELP | ROLE_COMPLEMENT | SHARED_CONTEXT
    "strength": 0.9,
    "why": "배포 권한 오류 ↔ 작년 CI 파이프라인 구축 경험",
    "opener": "민서님, 혹시 Actions 배포 권한 쪽 해보셨어요?"
  }
}
```

**왜 AI여야 하는가 (질문 대비)**
"배포에서 막힘"과 "작년에 도커 해봄"은 **태그가 겹치지 않는다.** 문자열 매칭으로는 절대 안 이어진다.
의미상 한쪽이 다른 쪽을 풀 수 있다는 판단은 LLM만 한다. 이게 `ASYMMETRIC_HELP`다.

**코드로 하는 것** (LLM에 안 맡긴다고 발표에서 명시)
같은 방 필터, 만료 검사, 중복 알림 차단, strength 임계값(0.6 미만은 버림), 동의 여부 확인.

### 4-3. 프롬프트 방어
note는 사용자 자유 입력이다. **다른 사용자의 note를 시스템 프롬프트에 넣지 않는다.**
데이터 블록으로 감싸 넣고, 지시문처럼 보이는 내용은 무시하도록 규칙을 둔다.

## 5. API

```
POST /room/{code}/join      { nick, school?, status, note? }  → { id }
POST /room/{code}/status    { id, status, note? }             → 200
POST /room/{code}/heartbeat { id }                            → 200
GET  /room/{code}/stream    (SSE)                             → 멤버 목록 + 접점 알림
POST /room/{code}/leave     { id }                            → 200
POST /match/{id}/react      { match_id, reaction }            → 200
```

실시간은 **SSE 또는 5초 폴링**이면 충분하다. 웹소켓 불필요.

## 6. PWA 주의사항

- **웹 푸시는 iOS에서 홈 화면 추가 후에만 동작한다.** 안드로이드는 정상. 발표에서 먼저 언급할 것
- **백그라운드 실행 없음.** 탭이 열려 있는 동안만 갱신된다. 그래서 하트비트 만료 설계가 필요하다
- `manifest.json` + 서비스워커 기본만. 오프라인 캐싱까지 갈 필요 없음
- QR은 방 URL을 그대로 담으면 된다. `https://.../r/KOSS26`

## 7. 시연 시나리오

> 이 절은 초안이다. **실제 8컷 대본은 [`scenario.md`](scenario.md)를 따른다** — 입장 한 화면,
> 46명 군중, BLE 채팅 컷까지 포함된 최신 버전이다. 여기는 API 흐름만 요약해서 남긴다.

1. 폰 두 대. 하나는 지원, 하나는 민서. QR 찍고 입장 — 닉네임·소속·상태·한 줄을 **한 화면에서**
2. 지원이 `LOOKING_FOR` 선택 + "Actions 배포에서 권한 오류로 막힘" 입력
3. 방 화면에 집계가 바뀐다. 46명 중 지원도 하나가 된다
4. 민서가 `CAN_SHARE` 선택 + "작년에 도커 CI 구축해봄"
5. **몇 초 뒤 지원 화면에 접점 카드가 뜬다.** 첫마디까지
6. BLE로 만날 자리를 정한다. 서버를 거치지 않는다
7. 마지막 컷: 서버에 뭐가 남는지 보여준다. 계정 없음, 하트비트 중단 5분 뒤 상태 만료 (후속 구현; 디스크 즉시 완전 삭제와 구별)

## 8. 지금 순서와 우선순위

1. **담당 3**: 방 만들기 + join/heartbeat + SSE. Redis로. 1시간
2. **담당 2**: 화면 3개. 더미 JSON으로 먼저 시작. 백엔드 안 기다린다
3. **담당 1**: 게이트웨이 호출 성공 → note에서 태그 추출 → 접점 매칭 프롬프트

### 자를 순서 (시간 모자랄 때 위에서부터 버린다)

| 순위 | 기능 | 버려도 되나 |
|---|---|---|
| 1 | PLACE 방 (일상 모드) | **버려도 됨.** 발표에서 어차피 슬라이드 한 장 |
| 2 | 상태 세트 전환 (MEETUP) | 버려도 됨. HACKATHON 하나로 시연 |
| 3 | 참가자 인증 배지 | 버려도 됨 |
| 4 | note → 태그 자동 추출 (P1) | 버려도 됨. 사용자가 직접 고르게 |
| 5 | 운영진 대시보드 | **화면만이라도 남겨라.** 숫자는 하드코딩해도 됨. BM 근거 |
| 6 | 접점 매칭 (P2) | **절대 못 버림. AI 점수 전부** |
| 7 | 방 입장 + 상태 + 목록 | **절대 못 버림. 제품 자체** |

**6번과 7번만 살아 있으면 시연은 성립한다.** 나머지는 전부 선택이다.
